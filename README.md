# disclosure-bot

Собирает данные о **покупках** акций из публичных раскрытий:

- **SEC EDGAR** — инсайдерские покупки (Form 4, код транзакции `P`): директора,
  топ-менеджеры и держатели >10% акций публичных компаний США.
- **House Clerk** — покупки конгрессменов США (Periodic Transaction Reports,
  требование STOCK Act).
- **BaFin** (Германия) — инсайдерские покупки немецких публичных компаний
  (Art. 19 MAR «Directors' Dealings», немецкий аналог Form 4). См. [bafin.py](bafin.py).
- **Oslo Børs / Euronext Oslo «Newsweb»** (Норвегия) — инсайдерские покупки
  норвежских публичных компаний (категория «Managers' transaction», местный
  аналог Form 4/Directors' Dealings). Полностью открытый JSON API, без входа и
  без ключа. См. [norway.py](norway.py).
- **Finansinspektionen «Insynsregistret»** (Швеция) — инсайдерские сделки
  шведских публичных компаний. Открытый CSV-экспорт: без ключа, без входа, с
  фильтром по дате сделки и со **структурированными** колонками (цена, объём,
  валюта, должность, тип инструмента). См. [sweden.py](sweden.py) и раздел ниже.
- **SEC Schedule 13D/13G** — крупные доли (от 5% акций компании). Отвечает на
  вопрос, на который не отвечает ни один другой источник: не «на сколько денег
  купили», а **какую долю компании** человек или фонд теперь держит. См.
  [sec_13dg.py](sec_13dg.py).
- **SEC Form 144** — уведомление о **намерении** продать, подаётся *до* сделки и
  потому до Form 4, который её фиксирует. Используется как ранний сигнал выхода.
  См. [sec_144.py](sec_144.py).
- **Senate eFD** (Сенат США) — вторая половина тех же раскрытий по STOCK Act.
  **Выключен по умолчанию** и сейчас недоступен: см. раздел «Сенат» ниже.
- **Крипто** — покупки биткоина/эфира компаниями на баланс (8-K/6-K), потоки
  в спот-ETF, крипто-покупки конгрессменов и (по флагу `--onchain`) движение монет
  с кошельков бирж. См. раздел «Крипто» ниже.

Все три формы SEC (4, 13D/G, 144) приходят из одного и того же дневного индекса,
поэтому добавление 13D/G и 144 не стоит ни одного дополнительного запроса к
индексу — только запросы за самими документами.

Все четыре выборки — **без ограничения по списку компаний** (любая публичная
компания США/Германии/Норвегии) и с суммой сделки **от 50,000** в валюте
источника (`--min-value`; для House — по нижней границе диапазона, т.к. точных
сумм там не бывает; норвежские кроны пересчитываются в евро по реальному курсу,
см. [fx.py](fx.py)). Ограничить SEC/House только S&P100+Nasdaq100 можно флагом
`--universe-filter` (см. [universe.py](universe.py)) — на BaFin/Норвегию это не
влияет.

**Валюта сигналов — евро.** Источники раскрывают суммы по-разному (SEC/House в
долларах, BaFin в евро, Осло в кронах), поэтому всё, что попадает **в сигнал**,
приводится к евро по актуальному курсу — иначе суммы из разных стран нельзя
сравнить глазами, а один порог означал бы разную реальную планку для разных
источников. Курсы берутся с Yahoo Finance и кэшируются на сутки; если сеть
недоступна — используется зашитый приблизительный курс, сигнал из-за этого не
теряется. **Сырой список сделок** (меню, CSV, база, построчные уведомления)
намеренно остаётся **в исходной валюте** — чтобы сходилось с документом
по ссылке.

## Что бот делает сейчас (кратко)

Этот раздел — актуальная сводка; ниже документ описывает части подробно, и в деталях некоторые
разделы отстают от неё. При расхождении верна сводка.

**Приходит само**

| Когда | Что |
|---|---|
| Пятница, 17:00 | Сигналы недели на покупку (до пяти, из них до двух монет) и сводка по счёту. Блок: тикер и «Invest», цена, стоп, сумма в евро, вердикт по графику, дата отчёта, если она близко |
| Любой день | Сигнал на продажу по вашим позициям; CFD-сигналы по монетам («CFD»); бумажные сделки форекс-лиги («CFD test») |
| 08:00 | Проверка уровней из прошлых разборов (`/watch`): при закрытии за уровнем — свежий разбор |
| 08:00, раз | Предупреждение, если компания из вашего портфеля под выкупом; если истёк вход Claude или TradingView |
| Первое число месяца | Таблица лиги; как сработали собственные сигналы бота (`/signals`) |

**Команды в Telegram**

| Команда | Что делает |
|---|---|
| `NVDA`, `BTC`, `EQNR.OL` | Короткий разбор: решение бота, цена, балл, график, тренд, диапазон, стоп, уровень ожидания, вывод |
| текст или `/ask …` | Ответ аналитика, до пяти строк |
| `/bought`, `/sold` | Запись своей сделки вне Trading 212: `/bought XRP 1.37 100`, `/bought XRP 1.37 €200`, `/sold XRP` |
| `/size` | Сумма сигнала: недельный бюджет (`/size budget 30`, делится по баллу, неизрасходованное переносится) или риск и предел доли счёта |
| `/signals` | Результат пятничных сигналов через 1, 4 и 12 недель против рынка |
| `/watch`, `/watch off XRP` | Уровни, которых бот ждёт после разборов |
| `/cfd`, `/cfd balance\|risk\|maxrisk\|off\|on` | CFD-сигналы по монетам и их настройки |
| `/cfd plan XAUUSD buy 4461.80 stop 4449.10`, `/cfd cancel 3` | Своя CFD-сделка: цели, объём, слежение |
| `/league`, `/league off\|on` | Бумажная лига форекс-идей (13 недель) |
| `/backtest NVDA` | История тикера после его же инсайдерских покупок |

Портфель в Telegram не показывается (`/portfolio` и `/crypto` отвечают, что он в приложении Trading 212);
в терминальном меню он остаётся.

**Откуда данные для аналитика** (по порядку): общественный сервер TradingView (`tradingview-mcp-server`
0.8.1, в отдельном окружении `~/Tools/tradingview-mcp-community`) — основной; официальный сервер TradingView
(`mcp.tradingview.com`, вход `claude mcp login tv`) — дополнение; TradingView Desktop — запасной. Вердикт по
графику считает сам бот по фиксированным правилам (`chart_check.py`), Claude его только проверяет. Новости —
сначала 8-K самой компании и Reuters/Bloomberg/WSJ/FT/CNBC/AP (`sources.news`).

**Что не отправляется в сигналы**: компания под выкупом (`takeover.py`); то, что вы уже держите; то, по чему
сигнал был в последние 30 дней.

**Обслуживание**: копия базы каждый день в `data/backups` (последние 14); `upkeep.py`.

## Швеция (Finansinspektionen)

Самый удобный из европейских источников. У FI есть открытый CSV-экспорт
(`marknadssok.fi.se`): без ключа, без регистрации, с фильтром по диапазону дат
сделки и с 23 структурированными колонками. Сравните с BaFin (у которого вообще
нет ленты последних сделок — приходится обходить алфавит A-Z, ~30-40 минут на
первый проход) и с Норвегией (где сумма лежит в свободном тексте и достаётся
регуляркой).

Кроме того, FI публикует то, чего нет ни у одного другого источника здесь:
**признак «сделка связана с программой акций»** (`Är kopplad till aktieprogram`).
Выданные по программе мотивации акции — это компенсация, а не решение купить;
по умолчанию такие строки в сигналы не идут (`--include-share-programs` вернёт).
По той же логике в денежные сигналы не идут не-акции (опционы, варранты,
облигации): они оцениваются по страйку или номиналу, а не по цене акции.

Три особенности, из-за которых код выглядит так, как выглядит:

1. **Экспорт молча обрезается на 1000 строках** и игнорирует собственный параметр
   `Page` — любая страница возвращает те же первые 1000 строк. Запросили период
   пошире — остальное просто пропало, без ошибки и без признака. Поэтому
   `fetch_rows()` идёт по периоду кусками и делит пополам любой кусок, который
   упёрся в лимит.
2. **CSV в UTF-16, разделитель `;`, десятичная запятая** (`1,196794`).
3. **Исправленная декларация публикуется заново целиком**, и старая версия при
   этом не всегда снимается: одна покупка Vin & Vind AB встречается пять раз, из
   них три помечены `Reviderad`, а **две так и остались `Aktuell`**. Поэтому
   строки хранятся с ключом по самой сделке (без времени публикации), и более
   поздняя публикация заменяет более раннюю — иначе суммы удваиваются.

Ограничить/пропустить: `--sweden-days N`, `--no-sweden`, `--sweden-only`.

## Крипто

Бот следит за тринадцатью монетами: **BTC, ETH** и одиннадцатью альтами — **SOL, XRP,
BNB, DOGE, AVAX, HYPE, LTC, ENA, LINK, TRX, SUI** (`model.COINS`; BTC и ETH — это
`model.MAJOR_COINS`, остальные — «альты»). Что питает каждую:

| Что | Для каких монет |
|---|---|
| Тренд (цены) | все тринадцать |
| Притоки и оттоки спот-ETF | BTC, ETH и SOL |
| Покупки и продажи компаний (8-K/6-K) | все тринадцать |
| Новости | все тринадцать |

Четыре источника, все без ключей. Все сигналы привязаны к тикеру вида
`CRYPTO:BTC` — с префиксом, потому что голый `BTC` это ещё и американский ETF
(Grayscale Bitcoin Mini Trust). Благодаря общему ключу покупка биткоина
конгрессменом, покупка компанией и приток в ETF автоматически находят друг друга
как «совпадение по источникам» (`cluster.find_corroboration`). Код —
[crypto.py](crypto.py) и [cluster/crypto.py](cluster/crypto.py).
`/bought HYPE 90` и `/sold SUI` работают для любой из тринадцати.

**Альты — отдельная осторожность.** Альт получает «покупку» только пока сам биткоин выше
своей 100-дневной средней (фильтр биткоина, см. «Оценка монеты»); в неделю приходит не больше
двух сигналов по монетам (сначала BTC и ETH, затем лучшие альты — см. «Недельный ритм»); а
в блоке покупки альта есть строка «High risk» (см. «Как выглядят сообщения»).
У BTC и ETH ни фильтра, ни пометки нет.

- **Конгрессмены** — строки PTR с типом актива `[CT]`. Раньше у 9 из 10 таких
  строк вообще не было тикера («Bitcoin [CT]»), и они не доходили до кластеров.
  Теперь это обычные строки Палаты с тикером `CRYPTO:BTC`: кластеры, выходы,
  рейтинг конгрессменов — всё как для акций.
- **Компании (treasury)** — [crypto_treasury.py](crypto_treasury.py). Полнотекстовый
  поиск EDGAR (efts.sec.gov) находит 8-K/6-K, где упоминается монета — по одному запросу на
  каждую из тринадцати (`QUERIES`: bitcoin; ether/ethereum; solana; XRP; BNB; dogecoin; AVAX;
  hyperliquid; litecoin; ethena; chainlink; TRX или TRON; SUI), затем
  из текста регулярками достаются сделки: прозой («purchased 1,355 bitcoin at an
  average price of approximately $79,475», «acquired 5,000,000 HYPE tokens») и таблицей
  Strategy («BTC Purchased … 950 $ 75.7 $ 79,670»). Берутся только явные сделки в прошедшем
  времени с количеством монет: «acquired 1,000 bitcoin mining machines», «may purchase up
  to», «holds 12,000 bitcoin» и продажа намайненного майнером — не сделки. Полное имя
  альта (solana, dogecoin, litecoin, avalanche, chainlink, hyperliquid, ethena) читается в
  любом регистре, как bitcoin; его тикер (SOL, XRP, BNB, DOGE, AVAX, HYPE, LTC, ENA, LINK, TRX,
  TRON, SUI) — только заглавными, с необязательным «tokens»/«coins» после: «link», «hype»,
  «sol» и «sui» в отчётах — обычные слова. Заглавный тикер альта, за которым идёт название компании
  или ценной бумаги — слово с заглавной буквы либо Inc, Corp, Corporation, Ltd, LLC, Holdings,
  Strategies, Group, shares, common, stock, properties, warrants, notes, units («500,000 SOL Strategies
  common shares», «100 TRON Inc shares»), — не монета (для BTC, ETH и полных имён правило не
  действует). Количество может быть со словом-множителем — «12.6 million HYPE tokens», «1.5 billion
  DOGE», «300 thousand LINK», «2.2m SOL»; простые числа перед BTC и ETH читаются, как читались. Цена в сделке проверяется по границам
  правдоподобия для каждой монеты (`PLAUSIBLE_PRICE_USD`: например SOL — $5–5 000,
  DOGE — $0,005–20): потерянный разделитель тысяч не превращается в сделку. Тикер
  компании — основной, из карты CIK (EDGAR перечисляет классы по алфавиту, и у
  BitMine первым стоит привилегированный BMNP).
  Покупки складываются в недельную сумму по монете (с понедельника): сигнал —
  когда неделя больше, чем 90% недель за прошлый год, и не меньше €50 млн для BTC и ETH
  (€10 млн для альтов); компания, купившая монету впервые, помечена «(впервые)». Рутинные
  еженедельные покупки Strategy сигналом больше не считаются. Продажа от €10 млн для BTC и ETH
  (от €5 млн для альтов) — сигнал осторожности. Продажа без суммы (ни в этом документе, ни в
  других по той же монете) оценивается как количество × текущая цена монеты (CoinGecko, кэш на
  час) и должна пройти тот же порог; если цены нет — продажа отбрасывается. Год истории для «нормы» подгружается один раз:
  `python crypto_treasury.py --backfill 365` (команда та же и для новых монет; её запускают
  вручную, не ежедневный прогон). В первый раз после перехода на тринадцать монет — с
  `--reread`: `python crypto_treasury.py --backfill 365 --reread` перечитывает и уже прочитанные
  документы (прежний разбор брал из них только BTC и ETH) и достаёт из них сделки альтов; уже
  сохранённые сделки не дублируются (ключ — сама сделка, `INSERT OR IGNORE`), а из
  `crypto_treasury_seen` ничего не удаляется. Ежедневный прогон по-прежнему пропускает
  прочитанные документы.
  Ежедневный прогон ищет по всем тринадцати запросам. Сбой одного запроса — после обычных
  повторов EDGAR (три попытки, паузы 2 и 5 с) — не теряет остальные: найденное сохраняется,
  сбой пишется в stderr, а источник считается упавшим, только если упали все запросы — или
  если EDGAR лежит: после трёх неудавшихся запросов подряд (`MAX_CONSECUTIVE_FAILURES`) поиск
  останавливается и источник считается упавшим, не тратя повторы на остальные монеты (найденное
  до этого уходит вместе с ним, следующий прогон ищет окно заново). (Раньше
  запросы шли подряд — bitcoin, затем ether — и первый же сбой обрывал поиск: прогон падал целиком,
  и находки другой монеты пропадали. Пропущенное находится в следующем прогоне: окно
  `--crypto-days` ищется каждый день, а документ помечается прочитанным только после чтения.)
  Количество монет в логе, в `purchases_log.csv` и в досье — обычным числом, без «1.25e+06».
- **Спот-ETF** — [crypto_etf.py](crypto_etf.py). Дневные потоки всех американских
  спот-фондов (12 на биткоин, 11 на эфир, 7 на SOL: BSOL, FSOL, GSOL, MSOL, SOEZ, TSOL, VSOL) —
  с таблиц Farside; при первом запуске подгружается вся история с запуска фондов. У SOL
  страницы «вся история» нет (`farside.co.uk/sol/` — только последние дни), поэтому её история
  копится по дням с первого запуска. «Необычно» считается относительно
  последних 126 торговых дней: день — в верхних 10% и не меньше пола дня, серия от 3 дней
  в одну сторону — в верхних 10% трёхдневных сумм и не меньше пола серии. Пока истории
  меньше 30 дней — фиксированные пороги. Все четыре числа — по монетам, у фондов SOL они на
  порядок меньше:

  | | BTC, ETH | SOL |
  |---|---|---|
  | Фиксированный порог дня (истории меньше 30 дней) | $400 млн | $50 млн |
  | Фиксированный порог 3 дней | $500 млн | $100 млн |
  | Пол дня (относительное правило) | $100 млн | $25 млн |
  | Пол 3 дней | $250 млн | $60 млн |

  Если Farside молчит больше 3 рабочих дней, для BTC и ETH берутся страницы BlackRock (IBIT и
  ETHA: изменение числа паёв × NAV), и сигнал пишет «только IBIT/ETHA» (для SOL запасного
  источника нет). Отток — сигнал осторожности.
- **Кошельки бирж** — [crypto_onchain.py](crypto_onchain.py), **выключено по
  умолчанию** (`--onchain`). Балансы нескольких крупных холодных кошельков
  Binance/Bitfinex/Robinhood (mempool.space и публичный Ethereum RPC; свой узел —
  `ETH_RPC_URL`). Вывод с бирж ≥ 2 000 BTC / 40 000 ETH за ~сутки читается как
  накопление, завод — как предложение. Это **не раскрытие**: метки кошельков
  общественные, а перекладывание монет самой биржей выглядит так же, — алерт
  говорит об этом прямо.

**Сигналы осторожности** — отток из ETF, продажа монет компанией, завод монет на
биржи. В Telegram они отдельно не приходят: модель учитывает их в оценке монеты
(осторожность, подтверждённая ценой, — минус 20 баллов и блок покупки, см.
«Оценка сигналов и сигналы на покупку» ниже), они записываются в журнал сигналов с пометкой
`caution`, а по монете, которая у вас в позиции, дают сигнал на продажу (см. «Позиции»
ниже). Завод на биржи попадает в журнал — а значит, может дать сигнал на продажу — только
если ежедневный прогон запущен с `--onchain`; `run_daily.sh` его не передаёт, а
сама оценка этот детектор не читает.

Балл у крипто-сигнала — «прошёл порог своего источника» плюс размер в евро
(`W_CRYPTO_*` в [cluster/common.py](cluster/common.py)): порядок внимания внутри
детекторов. Решение о покупке принимает оценка модели (см. «Оценка сигналов и
сигналы на покупку» ниже). Для бэктеста `CRYPTO:BTC` берётся как `BTC-USD`.

```bash
python bot.py --once --crypto-only              # только компании и ETF
python bot.py --once --crypto-only --onchain    # плюс кошельки бирж
python bot.py --once --no-crypto                # всё, кроме крипто
python bot.py --once --crypto-only --crypto-days 30   # поиск 8-K за 30 дней
```

## Крупные доли (13D/G) и намерения продать (Form 144)

**Schedule 13D/13G.** Перешагнув 5% акций компании, держатель обязан
задекларироваться: 13D — если может добиваться влияния на управление
(активист), 13G — если пассивный (индексные фонды и большинство институционалов).
Изменения подаются как поправки (`/A`).

Зачем это здесь: все остальные источники отвечают «кто купил и на сколько денег».
Этот отвечает **«какую долю компании»** — то самое `percentOfClass`. Именно его
заменял собой плоский денежный порог `*_SOLO_THRESHOLD` («данных о доле от общего
числа акций компании у нас нет»). €500k в компании за €50 млн и в компании за
€500 млрд — совершенно разные вещи, и до появления этого источника бот их не
различал.

Сигнал возникает, когда доля появилась впервые либо выросла минимум на
`--stake-min-increase` п.п. (по умолчанию 1). Без этого порога лента утонула бы в
поправках 13G/A, которыми индексные фонды отчитываются о десятых долях процента.
`--activist-only` оставит только 13D.

Техническая ловушка, стоившая отдельного разбора: **13D и 13G, при одном и том же
XML-namespace и одном регуляторном режиме, называют поля по-разному** —
`issuerCIK`/`issuerCik`, `dateOfEvent`/`eventDateRequiresFilingThisStatement`,
`percentOfClass`/`classPercent`, и разные контейнеры для отчитывающегося лица.
Читать только написание из 13D — это не ошибка, а пустой список. На оба варианта
есть тесты.

**Form 144** — уведомление о намерении продать. Подаётся *до* продажи и потому до
Form 4, который её зафиксирует: сигналы выхода видят разворот кластера на недели
раньше, чем по одним лишь продажам. В сигнале такие строки помечены отдельно
(«заявил о продаже (Form 144)»), потому что намерение — это не сделка: от него
отказываются, и продают часто меньше заявленного. Мелочь отсекается порогом
`cluster.FORM_144_MIN_VALUE` (по умолчанию $100k) — основной объём Form 144 это
рутинная продажа только что вестившихся RSU.

Form 144 приносит ещё и `noOfUnitsOutstanding` — число акций в классе, то есть
позволяет посчитать долю продажи от компании.

Ни в 13D/G, ни в 144 нет тикера — только CIK эмитента. Он резолвится через
[cik_map.py](cik_map.py) по официальному `company_tickers.json` от самой SEC.

Выбрать формы: `--forms 4,13D,13G,144` (по умолчанию все четыре).

## Сенат США (eFD) — выключен по умолчанию

`efdsearch.senate.gov` **сейчас отвечает HTTP 403 на любой запрос отсюда** — в том
числе с обычным браузерным User-Agent и ещё до шага с соглашением. В теле ответа
блокировка на уровне Akamai (`errors.edgesuite.net`), то есть это сетевой блок, а
не что-то, что делает не так наш код. Возможно, с другой сети всё работает.

Что **не** сделано в ответ на это: не подделывается User-Agent, не подбирается TLS-
отпечаток, не используется прокси. Этот проект уже проводил ту же черту — от
британской FCA/LSE отказались именно потому, что там требуется аккаунт или обход
гео-блокировки. Принять click-through соглашение, которое сайт сам показывает, —
нормально; обходить WAF, который нам отказывает, — нет.

Код написан ([senate_efd.py](senate_efd.py)) и включается флагом `--senate`, но по
умолчанию выключен и **не проверен на живых данных**. Логика кластеров/выходов у
Сената общая с Палатой представителей (тот же STOCK Act, те же вилки сумм) и
покрыта тестами.

**Великобритания (FCA/LSE)** — рассматривалась и отклонена. Все три
реалистичных пути оказались закрыты: официальный портал FCA (National Storage
Mechanism) требует регистрацию аккаунта; официальный API «RNS Data Feed»
требует выданные LSEG учётные данные (тоже регистрация); публичный London
Stock Exchange News Explorer отдаёт HTTP 451 (гео-блокировка) на страницах
самих новостей. Ни создавать аккаунты, ни обходить гео-блокировку бот не
будет — решено вместо этого подключить Норвегию (см. выше).

**Про SEC-покрытие**: бот сканирует **полный дневной индекс SEC** (все Form 4 за
день, ~800+ штук в обычный торговый день) за последние `--sec-days` календарных
дня (по умолчанию 2), а не «последние ~100 поданных документов» — той узкой
скользящей ленты, которую видно при разовой проверке раз в сутки, объективно не
хватает, чтобы поймать сколько-нибудь значимую долю дня (см. [sec_edgar.py](sec_edgar.py)
`scan_daily_index`).

**Про BaFin-покрытие**: у BaFin нет ленты «последние сделки» — только поиск по
первой букве имени инсайдера. Бот перебирает все буквы A-Z (+«Sonstige»),
листает страницы и для каждой ещё не виденной записи делает 2 дополнительных
запроса (список эмитентов → цена/объём сделки). Первый полный проход занимает
~30-40 минут (это разовая история — дальше только новые записи, быстро,
т.к. уже просмотренные ID пропускаются на первом же шаге). Ограничить буквами
для теста: `--bafin-letters A,B`; пропустить BaFin: `--no-bafin`.

**Про Норвегию**: в отличие от BaFin, у Newsweb есть нормальная лента с
фильтром по диапазону дат (`fromDate`/`toDate`), поэтому по умолчанию
сканируются только последние `--norway-days` дней (по умолчанию 2, как и SEC)
— для полного backfill за произвольный период поднимите значение, например
`--norway-only --norway-days 60`. Сумма/цена в тексте уведомления — не
структурированное поле, а свободный текст («...purchased 5,000 shares at an
average price of NOK 80 per share...»), поэтому парсится регуляркой; если
формулировка не распознана — документ просто пропускается (не попадает ни в
лог, ни в сигналы, т.к. проверить сумму нечем). Имя покупателя из текста тоже
best-effort — в редких случаях (нетиповые/пассивные формулировки) может
получиться неидеальным, но денежная сумма и тикер парсятся отдельными,
более надёжными регулярками и на это не влияют. Пропустить Норвегию:
`--no-norway`.

## Сигналы vs полный список

- **Сигнал** — тикер становится сигналом любым из двух путей. Сам по себе сигнал в
  Telegram не уходит: его оценивает модель (см. «Оценка сигналов и сигналы на покупку»
  ниже), а в Telegram по пятницам приходят сигналы на покупку — по одному сообщению на
  сигнал — и короткая недельная сводка по вашему счёту:
  1. **Кластер**: за короткое время купили несколько *разных* людей — разных
     корпоративных инсайдеров (SEC/BaFin/Норвегия, окно 14 дней), либо разных
     членов Конгресса (House, окно 45 дней — под срок подачи PTR по STOCK
     Act). Порог — минимум 2 покупателя (`SEC_MIN_BUYERS`, `HOUSE_MIN_BUYERS`,
     `BAFIN_MIN_BUYERS`, `NORWAY_MIN_BUYERS`).
  2. **Крупная одиночная покупка**: один человек в одиночку купил тикера на
     сумму от `*_SOLO_THRESHOLD` (по умолчанию **€500,000**, суммарно по всем
     его сделкам в том же окне) — данных о доле от общего числа акций компании
     у нас нет, поэтому это просто денежный порог «явно крупная ставка». Модель
     просит у детекторов пороги пониже — одиночная покупка от €250 000, сделки от
     €50 000 — а отсев делает уже её оценка.

  Пороги — в евро для всех источников (см. раздел про валюту выше). Учтите, что
  €500,000 — это примерно $580,000, т.е. для SEC/House планка чуть выше, чем
  если бы порог был в долларах. Вернуть прежнюю долларовую чувствительность
  можно флагом: `--solo-threshold 431000` (≈$500k) и
  `--min-cluster-value 86000` (≈$100k).

  Все четыре источника (SEC, House, BaFin, Норвегия) подключены и к сигналам, и
  к exit-сигналам ниже — только полный «сырой» список продолжает жить
  исключительно в меню/CSV.

  Пороги — в [cluster/common.py](cluster/common.py).

  **Когда сигнал повторяется.** Раньше правило было «только если выросло число
  покупателей», и это молча теряло сигналы. Окно кластера скользящее, старые
  покупатели из него выпадают: если по тикеру уже уходил сигнал на 4 инсайдерах,
  то новый кластер из 3 **других** людей через месяц не ушёл бы никогда (3 ≤ 4).
  А одиночная крупная покупка не могла повториться в принципе — у неё покупатель
  один и остаётся один, сколько бы он ни докупил. Теперь сигнал повторяется, если
  в нём появилось имя, которого не было в прошлый раз, **или** сумма выросла в
  `ALERT_VALUE_GROWTH` раз (по умолчанию в 1.5).

  **Кто именно покупает.** В сигнале теперь всегда видна должность, а кластер, в
  котором нет ни одного директора или топ-менеджера — только держатели >10% —
  помечен как `только держатели >10%`. Фонд, добирающий долю, и люди, управляющие
  компанией, — разные события, а по одним суммам они выглядели одинаково (самый
  крупный сигнал в базе — фонд, а не инсайдер). `--insiders-only` оставит только
  officers и directors.

  **Деривативы.** Строки code-P из деривативной таблицы Form 4 (варранты, опционы,
  конвертируемые) больше не суммируются с обыкновенными акциями: они оценены по
  страйку, а не по цене акции, и искажали итог. Вернуть: `--include-derivatives`.
- **Полный список всех покупок** (без кластеризации, каждая по отдельности)
  копится в SQLite (`data/disclosures.db`) и `data/purchases_log.csv` —
  смотрится из терминала, в Telegram не идёт.

## Сигналы выхода (exit signals)

Второй тип сигнала: когда несколько человек, которые вместе покупали тикер,
позже начинают его продавать — то есть кластер, похоже, разворачивается.
Пример: 28.08 было 5 покупок AAPL разными инсайдерами; через месяц 3 из этих
же 5 продали — по пятницам в Telegram придёт сообщение
`🔴 AAPL!: продают те, кто покупал — Anna Lee, Bo Chen, …` с тикером и именами продавших
(первые пять, дальше «и ещё N»);
сам сигнал — `ВЫХОД: AAPL — 3 из 5 инсайдеров...` со ссылками на конкретные покупку
и продажу каждого — виден в терминале и в журнале сигналов (`strategy.exit_signals`
в [strategy.py](strategy.py)).

Правило (константы `EXIT_*` в [cluster/common.py](cluster/common.py)):
- Смотрим на покупателей тикера за последние 12 месяцев (`EXIT_LOOKBACK_MONTHS`).
- Нужно минимум 2 изначальных покупателя (`EXIT_MIN_BUYERS`).
- Сигнал срабатывает, когда **хотя бы половина** из них (`EXIT_SELL_FRACTION`) и
  при этом не менее 2 человек (`EXIT_MIN_SELLERS`) позже продали тот же тикер
  (для каждого — сравнивается именно его личная дата продажи с его личной датой
  покупки, не общая по кластеру).
- Как и с сигналами покупки, повторно не шлётся, пока число продавцов не выросло.

Для этого бот теперь также хранит **продажи** (SEC: код транзакции `S`,
отдельная таблица `sec_sales`; House: типы `S`/`S (partial)`, та же таблица
`house_purchases` — да, теперь не только покупки, несмотря на имя, см.
комментарий в [db.py](db.py); BaFin/Норвегия: `txn_type = 'S'` в
`bafin_purchases`/`norway_purchases`, тоже несмотря на имя) — но в основной
лог/CSV «покупок» продажи не попадают, они используются
только для расчёта exit-сигналов.

**Form 144 как ранний сигнал.** Кроме состоявшихся продаж, выходом считается и
поданное уведомление о намерении продать (Form 144) — оно подаётся до сделки и
потому до Form 4, который её зафиксирует. В сообщении такие строки помечены
отдельно («заявил о продаже (Form 144)»), потому что намерение — это не сделка.
Отключить только их: `find_sec_exit_signals(..., include_form_144=False)`.

Имена между Form 4 и Form 144 пишутся по-разному (Form 4 — «CHEN SEAN», Form 144 —
как ввёл заполнитель, часто «Sean Chen»), поэтому для сопоставления используется
нормализованный ключ (регистр, пунктуация, суффиксы вроде Jr., сортировка слов).
Инициалы при этом **сохраняются**: склеить «Smith John A» и «Smith John B» — значит
выдумать сигнал о продаже, а это хуже, чем пропустить совпадение.

Отключить: `python bot.py --once --no-exit-signals`.

## Досье по тикеру или монете

```bash
python research.py INBX
python research.py DE0007190001     # ISIN тоже принимается
python research.py BTC              # монета
python research.py '$BTC'           # акция с таким тикером (Grayscale Bitcoin Mini Trust), не монета
python research.py EQNR.OL          # европейская акция с суффиксом биржи
```

Весь остальной проект — это шланг, направленный на то, что происходит сегодня. Это
обратное направление: вы называете компанию или монету, а инструмент собирает всё,
что о ней записано, в одном месте.

**Что можно ввести** (один резолвер — `assets.py` — общий для Telegram, меню и
`research.py`, правила проверяются по порядку):

1. ISIN (как называют эмитента BaFin / Finansinspektionen) — этот эмитент, как акция;
2. `$XYZ` — всегда акция (`$BTC` — это Grayscale Bitcoin Mini Trust ETF, не биткоин);
3. `CRYPTO:XYZ` или `XYZ-USD` — явно монета;
4. символ с суффиксом биржи (`.OL .ST .DE .CO .HE .PA .AS .L .SW .MI .MC`) — листинг
   на этой бирже;
5. символ из списка монет (~250 крупнейших по капитализации, кэшируется раз в
   сутки) — монета; при совпадении монета побеждает акцию, поэтому голый `SOL` — это
   Solana, а `BTC` — биткоин, а не одноимённый тикер. **Исключение — крупные акции
   США**: символ из списка S&P 100 ∪ Nasdaq-100 ([universe.py](universe.py)) — это
   акция, даже если такая монета тоже есть: `DASH` — DoorDash, `STX` — Seagate,
   `APP` — AppLovin. Монету с таким тикером пишите явно: `DASH-USD`;
6. всё остальное, похожее на тикер, — американская акция или ETF;
7. ничего не подошло — ответ-подсказка с примерами, в очередь ничего не ставится.

Telegram до постановки в очередь проверяет, что символ существует: у акции или у
монеты не из списка (`CRYPTO:FOO`, `FOO-USD`) должна найтись цена хоть в одном
источнике. Иначе ответ «Не нашёл такой тикер: FOO (или источники цен сейчас не
отвечают)» — полный сбой всех источников цены выглядит так же, как несуществующий
тикер. Ответ по монете заканчивается строкой «Нужна акция? Напишите $BTC».

Считается только первое слово сообщения (`"aapl buy now"` — это `AAPL`), как было
всегда для Telegram.

Для акции и ISIN отчёт собирает:

- размер компании, оборот, биржа, отрасль;
- поведение цены за 1/3/6/12 месяцев — **и относительно бенчмарка**, потому что
  покупка инсайдера после падения на 60% и покупка на росте читаются по-разному, а
  сырая лента этой разницы никогда не показывала;
- **что говорят аналитики** — консенсус-рейтинг, как он менялся за последние
  месяцы, средняя целевая цена с диапазоном, и последние изменения рейтингов по
  фирмам. Это мнения третьих сторон, с атрибуцией, а не прогноз бота (см. ниже);
- **финансы** — выручка / операционная и чистая прибыль / свободный денежный поток
  / кэш / долг за последние 3–4 года со стрелками тренда (Yahoo Finance);
- **годовой отчёт (10-K/20-F)** — выручка / чистая прибыль / активы /
  обязательства / операционный денежный поток напрямую из XBRL самой компании
  (не смешанные по кварталам данные Yahoo, а именно то, что подано в годовом
  отчёте), с изменением год к году. Плюс текстовый поиск по самому документу на
  три конкретных, стандартизированных раскрытия — сомнения в способности
  продолжать деятельность (going concern), выявленный существенный недостаток
  внутреннего контроля, пересчёт отчётности — с цитатой дословно и ссылкой на
  документ. Ничего не суммируется и не оценивается: либо формулировка нашлась,
  либо нет;
- **акции в обращении** — число акций по годам из XBRL самой SEC: компания
  размывает акционеров или проводит обратный выкуп. Стоит прямо под блоком
  инсайдерских покупок специально — это разные картины;
- **структура владения** — доля инсайдеров и институционалов, число фондов, топ-5
  институциональных держателей с изменением за квартал (Yahoo Finance). Дополняет
  13D/G, который ловит только доли от 5%;
- **короткие позиции** — процент фри-флоата в шорте, рост/падение против прошлого
  месяца, дней на покрытие (Yahoo Finance / FINRA). Высокий шорт при инсайдерских
  покупках — характерная конфигурация;
- **отчётность** — дата ближайшего отчёта и beat/miss за последние кварталы
  (Yahoo Finance). Сигнал прямо перед отчётом значит другое;
- **TradingView** — технический рейтинг TradingView, RSI, MACD, положение цены
  относительно 50- и 200-дневной средней, доходность, P/E, β. Работает и по ISIN
  (TradingView сам его резолвит). См. отдельное предупреждение ниже;
- все покупки и продажи инсайдеров из базы, с ролями и пометками
  «дериватив» / «план 10b5-1»;
- европейские инсайдеры (BaFin / Осло / Finansinspektionen) — ищутся и по ISIN;
- крупные доли 13D/G с процентом от компании;
- заявленные намерения продать (Form 144);
- сделки политиков по этой бумаге;
- какие сигналы бот уже присылал и с каким баллом, и по скольким независимым
  источникам эта бумага вообще засветилась за всё время (и отдельно — за последние 30 дней, если список отличается);
- **что компания сама подавала в SEC** (8-K, 10-Q, 10-K…) со ссылками;
- **свежие новости** с указанием издателя и ссылкой.

Для монеты (`crypto_research.py`) отчёт другой — там нет SEC, инсайдеров и
опиниона (ниже), а вместо них:

- цена сейчас и изменение за 7 дней / 30 дней / год, тренд к SMA50/SMA200,
  дневная волатильность за 30 дней;
- технический рейтинг TradingView (там, где он резолвит монету);
- своё, что бот уже видел по этой монете: покупки/продажи в казну компаний
  (crypto_treasury), притоки/оттоки спот-ETF, сделки политиков, приток/отток с
  бирж (on-chain, когда включено);
- свежие новости (CoinDesk / Cointelegraph, отфильтровано по названию монеты);
- прогноз на месяц (см. ниже) — для монеты это главное число, замены опиниону
  для крипты нет.

Ни одного ключа и ни одного аккаунта для этого не нужно: отчётность берётся из
`data.sec.gov`, новости — из агрегатора Yahoo Finance (уже зависимость проекта).
Цены, индикаторы, аналитика и список монет — из цепочек источников, каждая со
своим запасным вариантом на случай, если первый недоступен
([sources.py](sources.py)):

| Данные | Цепочка источников |
|---|---|
| История цены | акции: Yahoo (yfinance) → Nasdaq API `historical` (только США); монеты: Yahoo (`SYM-USD`, только если сходится с биржей, см. ниже) → Binance `klines` → Bybit `kline` → Kraken `OHLC` — берётся первый, где не меньше min(дней, 200) дневных баров, иначе самый длинный ряд из ответивших |
| Текущая цена | акции: Yahoo → TradingView scanner `close` → Nasdaq (только США); монеты: Binance ticker → Bybit ticker → CoinGecko `simple/price` → TradingView → Yahoo |
| Индикаторы | TradingView scanner → посчитано локально по истории цены (RSI 14, SMA50/200) |
| Цели аналитиков | только акции: Yahoo → Nasdaq API `targetprice` (только США) |
| Новости | Yahoo → Google News RSS → монеты: RSS CoinDesk + Cointelegraph, отфильтровано по названию/тикеру |
| Список монет | CoinGecko `coins/markets` (топ-250) → CoinPaprika `tickers` → встроенный список `crypto.SYMBOLS` |

Если источник не первый в цепочке, отчёт говорит об этом коротко, например
«цены: Binance (Yahoo недоступен)». Если вся цепочка для какого-то раздела не
ответила, этот раздел (и только он) показывает «недоступно сейчас» — остальной
отчёт всё равно приходит (у аналитиков — «нет данных»: отсутствие покрытия
выглядит так же, как сбой).

**Почему у монет Yahoo под подозрением.** Yahoo заводит монеты с одинаковым
символом под номерными тикерами, так что простой `SYM-USD` бывает совсем другой
монетой: `M-USD` закрывался по 0.00029, когда MemeCore (M) торговался по 1.22.
Поэтому текущая цена монеты берётся сначала с бирж, а историю от Yahoo (он первый —
только у него хватает глубины для проверки на истории ниже) бот принимает, лишь
если её последняя цена отличается от спот-цены биржи (Binance → Bybit → CoinGecko)
не больше чем на 10%; иначе история берётся с Binance и дальше по цепочке.

**Монета, у которой мало истории.** Порядок цепочки не решает сам: источник с коротким
рядом не прячет источник с длинным. HYPE нет на Yahoo, на Binance она с 24.09.2026
(11 баров), на Bybit — весь год (421 бар): берётся Bybit, потому что в первом источнике
цепочки нет 200 баров. Если ни в одном источнике их нет, берётся самый длинный ряд, а не
первый. У позиции по такой монете (`/bought HYPE`, `/bought SUI` — на Yahoo у них нет символа)
цена — последний завершённый бар этого ряда (`positions.last_close`), и по ней считаются
стоп и сигналы на продажу; тренд для подтверждения осторожности (`crypto.price_trend`)
берётся оттуда же. Для акций ничего не меняется.

### Прогноз на месяц

Каждый отчёт по акции или монете заканчивается блоком `📈 Прогноз на месяц`: не
вердикт «покупать», а историческая частота роста цены через месяц в похожих
ситуациях, посчитанная по прошлым данным ([outlook.py](outlook.py), дизайн —
docs/superpowers/specs/2026-09-23-any-asset-lookup-design.md). ISIN — исключение:
сопоставить его с торговым символом надёжно нельзя, поэтому прогноза по нему нет
(«нет свежих цен»), как и у остальных цен/новостей/отчётности — см. предупреждение
про ISIN ниже.

**Ситуация** — три грубых факта по дневным ценам закрытия, дающих 3 × 3 × 2 = 18
комбинаций:

- **тренд**: вверх (цена > SMA50 > SMA200), вниз (цена < SMA50 < SMA200) или
  смешанный;
- **движение за последний месяц**: сильный рост / сильное падение (больше своего
  обычного месячного разброса) или в пределах него — «плоско»;
- **волатильность**: высокая (выше 75-го перцентиля своей же истории) или обычная.

**Две таблицы**, построенные по наблюдениям раз в месяц на актив (каждый 21-й
торговый день для акций, 30-й день для монет — чтобы пересекающиеся окна не
раздували счётчики):

- акции — ≈170 крупных бумаг США (S&P 100 ∪ Nasdaq-100, [universe.py](universe.py))
  с доступной историей за ~15 лет. Европейские акции с суффиксом биржи
  используют эту же таблицу (в строке помечено «таблица по акциям США»);
- монеты — до 50 крупнейших монет по капитализации, у которых ≥ 2 лет истории, без
  всего, что не имеет собственной цены: стейблкоинов; символов не из 2–10 латинских
  букв и цифр (`FIGR_HELOC`); обёрнутых, застейканных и мостовых копий (WBTC, stETH)
  и токенизированных долларов, трежерис, золота и фондов — по словам в названии
  (wrapped, staked, bridged, restaked, liquid staking, usd, dollar, treasury, gold,
  yield, fund); и монет с привязанным курсом — дневной разброс за последний год
  меньше 0.5% (у крупных монет 2–5% в день, у привязанных около 0.1%). Сколько
  монет реально вошло, хранится вместе с таблицей и видно в строке прогноза: «по N
  крупнейшим монетам».

**Проверка на истории (walk-forward)**: для каждого года считается, была бы у
частоты по ситуации своя предсказательная сила *до* того, как этот год наступил
(обучение на всех годах раньше, проверка по Brier score на самом этом годе).
Наблюдение относится к году, когда стал известен его исход (конец месяца), так
что декабрьское наблюдение с исходом в январе не подглядывает в тестовый год.
Преимущество засчитывается, только если выполнено всё сразу:

- ≥ 50 наблюдений вне выборки;
- ситуация встречалась хотя бы в 3 тестовых годах;
- её Brier score лучше, чем у базовой частоты, хотя бы в 60% этих лет;
- и в сумме лучше хотя бы на 0.5% (Brier skill ≥ 0.005).

Раньше хватало первого условия и «в сумме лучше». На симулированных таблицах чистого
шума с общим для всех активов рыночным движением такое правило находило
«преимущество» у 19–25% ситуаций, у которых его нет; строгое — не больше ~6%, и
при этом всё ещё находит ~73% реальных эффектов в +8 п.п. У ситуации без
подтверждённого преимущества над простой средней долей роста по всей таблице
отчёт так и пишет: «нет преимущества над базовой частотой (обычно N%)» — вместо
числа по конкретной ситуации.

Таблицы **пересобираются раз в неделю** сами (`outlook.refresh_if_stale`,
встроено в ежедневный прогон); принудительно — `python outlook.py --rebuild`.
Между пересборками прогноз просто читает уже посчитанные таблицы, ничего не
переобучая на лету.

Это **частота в прошлом, не гарантия** — так и подписан каждый блок: не
предсказание, а то, как часто похожая ситуация заканчивалась ростом за
последние ~15 лет по акциям и несколько лет по монетам.

**Смещение выжившего.** Обе таблицы построены по *сегодняшним* участникам: акции —
по нынешнему составу S&P 100 ∪ Nasdaq-100, монеты — по нынешнему топу по
капитализации. Кто за эти годы вылетел из индекса или из топа (часто — после
падения), в таблицы не попал, поэтому базовая частота роста завышена, особенно у
монет: сегодняшний топ — это по определению те, кто вырос.

### Опинион (Buy / Lean Buy / Hold / Lean Avoid / Avoid)

До 2026-09-16 у проекта был другой, обратный принцип: только факты, никогда
«стоит ли покупать» — превращать раскрытия в такой ответ означает давать
инвестиционный совет, для которого нужны лицензированный консультант и знание
обстоятельств конкретного человека, которых у скрипта нет. Этот раздел README
годами так и назывался. Изменено по прямой просьбе пользователя, после того как
это противоречие было ему явно озвучено и подтверждено трижды подряд.

**Как это устроено.** [opinion.py](opinion.py) — отдельный модуль, детерминированная
взвешенная свёртка (без LLM) того, что дальше уже собрано в этом же отчёте:
баланс покупок/продаж инсайдеров и политиков за последний год, тревожные флаги
из годового отчёта (going concern / material weakness / restatement — тяжёлый
минус), тренд выручки/прибыли/денежного потока по SEC XBRL, консенсус аналитиков
и подразумеваемый потенциал, свежие 13D/G доли, тренд владения институционалами,
моментум цены к SPY, технический рейтинг TradingView и заголовки новостей
(сознательно с маленьким весом каждый — TradingView механический, а новости
считаются грубым keyword-совпадением по списку бычьих/медвежьих слов, без
понимания контекста и отрицаний; для настоящего разбора новостей — спросить
Claude напрямую, не автоматизировано). P/E и шорт-интерес **не оцениваются**:
P/E без отраслевого сравнения вводит в заблуждение, а высокий шорт сам по себе
не однозначно медвежий (может быть и сетапом для сквиза) — оба показаны как
данные, не как вклад в балл. Меньше двух значимых факторов или ISIN вместо
тикера — опиниона не будет вообще, а не число из почти ничего.

Каждый фактор показан отдельной строкой с его вкладом в балл — не чёрный ящик.
Веса выбраны рассуждением, как и в `cluster.score_signal`: **отправная точка,
не находка**, не бэктестировано, не лицензированная консультация.

Четыре честных ограничения, которые инструмент проговаривает сам:

- **Раздел TradingView несёт более жёсткое предупреждение, прямо в выводе.**
  Технический рейтинг TradingView — механическая свёртка ~26 индикаторов моментума
  и тренда: меняется внутри дня, смотрит только назад, не имеет доказанной
  предсказательной силы. Он показан — вместе с их собственной пометкой «Strong
  Buy» / «Sell» — так же, как показывают P/E: число, на которое смотрит рынок,
  посчитанное кем-то другим, одинаковое для всех пользователей TradingView, — а не
  рекомендация и не мнение бота. Всё остальное в этом разделе (RSI, MACD,
  положение относительно средних) — просто констатация состояния индикаторов.
  Эндпоинты TradingView недокументированы и могут измениться без предупреждения,
  как парсер PDF Палаты; при сбое раздел просто пропускается.

- **Раздел «Аналитики» — это чужие мнения, а не прогноз бота.** Целевые цены
  sell-side систематически завышены и часто не сбываются; раздел так и подписан.
  «Текущая цена», от которой считается потенциал роста, берётся из *нашей* истории
  котировок, а не из блоба yfinance — он у мелких и переименованных бумаг устаревший
  (у одной из бумаг в базе там цель в 2.4 раза выше реальной цены). Если цель
  расходится с ценой более чем втрое — она отбрасывается как устаревшая; если
  сильно, но меньше втрое — рядом ставится пометка «либо устарело, либо
  спекулятивная бумага».
- **Новости идут из агрегатора смешанного качества** — рядом стоят информагентства
  и сайты, недалеко ушедшие от форумов. Издатель печатается у каждого заголовка
  именно поэтому. И движение цены на заголовке не является доказательством, что
  заголовок был правдой.
- **По ISIN пропускаются цена, новости, отчётность SEC, аналитики, финансы,
  владение, шорт и даты отчётов.** yfinance охотно вернёт какой-нибудь ряд и на
  ISIN, но подтвердить, что это тот самый эмитент, нечем, — показать чужую бумагу
  хуже, чем не показать ничего. Раздел TradingView — исключение: их поиск
  сопоставляет ISIN с торговым символом сам.

### Один объединённый вердикт в Telegram

Напишите тикер или монету одним словом боту в Telegram — в ответ придёт **одно**
короткое сообщение примерно через минуту: блок (решение бота, цена, балл, вердикт по графику, тренд,
диапазон, стоп и, если вывод — ждать уровня, строка «Wait   close above …») и не больше двух строк под ним
(см. «Что бот делает сейчас»). Опинион, вход/цель аналитиков и новости в ответ больше не копируются: это
входные данные аналитика. Раньше это были два сообщения (быстрый опинион сразу, качественный разбор
позже по расписанию) — объединено в одно по прямой просьбе пользователя, который
явно принял задержку в обмен на цельный ответ вместо двух частичных. Механика:
`telegram_bot.py` кладёт тикер в очередь (`db.enqueue_analysis`) и сразу же,
синхронно, запускает `run_claude_analysis.sh` (не дожидаясь следующего планового
запуска по расписанию) — это единственное, что реально читает новости и график и
рассуждает, headless-Claude (см. «Аналитик (TradingView)» ниже), а не
keyword-подсчёт. Если после этого прогона строка тикера так и не получила ответа (не
уложился в 7 минут, упал или не дошёл до неё), `telegram_bot.py` откатывается на
быстрый ответ только по `opinion.py`, а строка в очереди остаётся необработанной и её
подхватит следующий плановый прогон. Любой другой текст —
вопрос аналитику, а не тикер: см. тот же раздел.

`/backtest TICKER` — как этот тикер торговался после своих же прошлых
инсайдерских покупок (см. раздел про backtest ниже — почти всегда `n`
слишком мал, чтобы это что-то значило на уровне одного тикера). Для полного
текста досье — по-прежнему `python research.py TICKER`. Ваши покупки:
`/bought` и `/sold` — см. «Позиции» ниже. См. [telegram_bot.py](telegram_bot.py), [opinion.py](opinion.py) и
раздел про автозапуск ниже.

## Ранжирование сигналов

Раньше все сигналы были равны: один прогон присылал 252 штуки плоским списком, что
почти то же самое, что не присылать ничего — самое заметное тонуло среди всего
остального. Теперь каждый сигнал получает **балл** (`cluster.score_signal`), и
список сортируется по нему. Решение о покупке принимает не этот балл, а оценка
модели (см. «Оценка сигналов и сигналы на покупку» ниже).

Балл — это **порядок внимания, а не прогноз доходности**. Он складывается из того,
на чём вообще построен инструмент:

| Компонента | Почему |
|---|---|
| Каждый дополнительный покупатель | Несколько независимых людей, сошедшихся на одной бумаге, — исходная идея всего проекта |
| Есть директор или топ-менеджер | Люди, управляющие компанией, знают о ней больше, чем пассивный держатель >10% |
| Доля от капитализации | €500k — это контроль в компании за €5 млн и округление в компании за €500 млрд |
| Прирост к своей позиции | Добрать 0.5% к пакету и удвоить его — разные события |
| Первая покупка в этой бумаге | Первая покупка после долгого молчания заметнее двадцатой |
| Свежесть раскрытия | Form 4 приходит через ~2 дня, PTR Палаты — в среднем через 14 |
| Бумага засветилась ещё в одном источнике | Независимая система раскрытия — инсайдеры, политики — тоже заметила эту бумагу за последние 30 дней |
| −штраф: неизвестный размер | Неизвестно ≠ мало |
| −штраф: низкая ликвидность | Бумага с оборотом €0.2 млн/день — это другая история, чем €30 млн/день |

**Каждая компонента ограничена сверху.** В первой версии слагаемое за долю от
капитализации было неограниченным, и одна нано-компания, у которой покупка вышла в
226% капитализации (устаревшая котировка), получила 18 161 балл при нормальном
диапазоне 20–60 — то есть одна кривая цифра отсортировала весь список. Ранжирование
обязано деградировать плавно, когда входные данные врут, потому что рано или поздно
они врут.

**Совпадение по источникам — тоже факт, а не мнение.** Если по одной и той же
бумаге за последние 30 дней уже отметилась независимая система раскрытия — не
только SEC, а, например, ещё и Сенат — сигнал получает бонус к баллу
(`cluster.find_corroboration` находит совпадение → `cluster.score_signal`
начисляет за него балл), а в самом алерте появляется строка «🔗 Другие
источники по этому тикеру: ...». Это не заявление, что источники согласны:
выход одного инсайдера и покупка другого на той же бумаге тоже считаются
совпадением — просто «здесь была активность по независимому каналу», не
больше. У SEC, Палаты, Сената и Осло сигналы привязаны к тикеру, а у BaFin и
Finansinspektionen — к ISIN, поэтому по-настоящему межстрановое совпадение
возможно только между этими двумя (BaFin ↔ Finansinspektionen): тикер одной
бумаги с ISIN другой не сравнивается. Досье по тикеру показывает то же самое
за всю историю, в разделе «Сигналы, которые бот уже присылал».

Флаги `--min-score` и `--min-liquidity` больше ничего не отсеивают: они лишь
помечают ручной, отфильтрованный прогон — в нём сигналы не оцениваются, покупки недели не
выбираются, а недельные сообщения ждут полного прогона (то же делают `--sec-only`,
`--house-only` и остальные `--*-only`).

Размер компании и оборот берутся из [marketcap.py](marketcap.py) и кэшируются на
неделю. Покрытие честное, а не полное: US-тикеры и Осло/Стокгольм резолвятся, а
BaFin и Finansinspektionen идентифицируют эмитента по ISIN, который надёжно не
резолвится — там размер остаётся неизвестным.

## Проверка сигналов на истории (backtest)

Самое важное, чего у бота не было: **способа узнать, работают ли его сигналы**. Восемь
источников, функция оценки — и ни одной проверки против того, что было с ценой
дальше. Все пороги в [cluster/common.py](cluster/common.py) выбраны рассуждением о предметной
области и никогда не сверялись с исходом.

```bash
python backtest.py               # по отправленным сигналам (signal_journal)
python backtest.py --purchases   # по отдельным покупкам SEC — работает уже сейчас
python backtest.py --ticker AAPL # только по этому тикеру (окно 10 лет; = /backtest в Telegram)
python backtest.py --opinions    # по журналу opinion.py (opinion_journal) — см. ниже
python backtest.py --horizon 5   # горизонт в торговых днях (по умолчанию 21)
```

**`--ticker`** — то же самое, чем отвечает `/backtest TICKER` в Telegram-боте
([telegram_bot.py](telegram_bot.py)): как этот тикер торговался после **своих же**
прошлых инсайдерских покупок. Почти всегда `n` намного меньше 30 — у одного тикера
просто мало событий — так что это почти никогда не «находка», отчёт сам об этом
говорит. Отдельный вопрос от «работает ли opinion.py» — см. ниже.

**`--opinions`** — читает `opinion_journal`: каждый посчитанный `opinion.score()`
записывается туда автоматически (`research.build()` → `db.journal_opinion`, одна
строка на тикер в день). `opinion.py` не существовал раньше, поэтому его нечем
проверить задним числом — эта таблица начинает копиться только с того момента, когда
тикер впервые проверили, и `--opinions` полезен не раньше, чем через месяцы
накопления.

Вход считается **по дате раскрытия, а не по дате сделки**: до подачи формы сделка не
публична, и мерить от даты сделки — значит записывать себе движение, которым никто
не мог воспользоваться.

Каждый сигнал записывается в момент отправки в таблицу `signal_journal` вместе со
всеми признаками, которые у него тогда были. Это принципиально: если восстанавливать
сигналы из строк покупок сегодняшним кодом и сегодняшними порогами, любая проверка
будет соглашаться с текущими настройками, потому что она из них и выведена.

Отчёт честен насчёт своих ограничений и печатает их сам:

- группы меньше `n=30` помечаются «too few to read anything into»;
- `p` — двусторонний точный биномиальный тест против монетки, **без** поправки на
  число сравниваемых групп;
- и главное — **наблюдения здесь не независимы**. Покупки скапливаются в одних и тех
  же бумагах и делят один период рынка, поэтому растущий рынок поднимает сразу все
  группы, а тест это переоценивает. Это не лечится накоплением строк за месяц.

Первый же прогон дал повод: у деривативных строк (code-P по деривативной таблице)
медиана −17.9 п.п. против бенчмарка при 0% попаданий — что независимо подтверждает
решение исключить их из денежных сумм. Но n=12, и отчёт это прямо помечает.

## Оценка предсказательной силы (walk-forward модель)

`backtest.py` меряет, что было с ценой после сигналов, по группам признаков.
`model_eval.py` идёт дальше и задаёт вопрос прямо: **есть ли у этих признаков
предсказательная сила вне выборки?**

```bash
python model_eval.py politicians    # House PTR-покупки — оценивается сейчас (данные 2025)
python model_eval.py insiders       # SEC Form 4 — «мало данных» ещё несколько месяцев
python model_eval.py                # оба
python model_eval.py --horizon 5 --folds 4
```

Что делается: логистическая регрессия и градиентный бустинг обучаются
предсказывать «обгонит ли бумага S&P за месяц» по признакам, которые бот и так
пишет (сумма/роль/размер компании/лаг раскрытия/размер кластера/цена до сделки).
Оценка — **walk-forward**: обучаемся на месяцах 1…N, проверяемся на N+1, катимся
вперёд, без заглядывания. В отчёте — AUC вне выборки с разбросом по фолдам,
калибровка, коэффициенты, и строка-вывод, привязанная к AUC.

**Жёсткий порог данных.** Ниже минимума (80 размеченных строк, 3 фолда по ≥12
строк) отчёт не печатает метрики, а пишет «мало данных, вернитесь примерно
тогда-то». Инсайдерский корпус этот порог сейчас не проходит (6 недель истории).
Политический — едва проходит на данных 2025 года (~150 строк от 20 конгрессменов),
и почти наверняка покажет AUC ≈ 0.5 и «нет заметного преимущества». Это ожидаемый
и правильный результат: несколько сотен сделок — этого не хватит, чтобы найти
преимущество, если оно вообще есть.

Чего здесь **нет** и не будет: сохранённой модели, оценки живого сигнала, вывода
«покупать» по конкретному тикеру. Модель переобучается каждый прогон только ради
оценки. Запускается только сам по себе (`python model_eval.py`): ни один модуль
проекта её не импортирует, и есть тест, который это проверяет.

## Оценка сигналов и сигналы на покупку

Бот **не ведёт портфель** — ни настоящий, ни виртуальный: ваш счёт Trading 212 — единственный
портфель, который он отслеживает (см. «Trading 212»). Бот ничего не покупает и не продаёт; он делает
три вещи:

1. **оценивает** сигналы — каждый день, одной стратегией для акций и монет: балл от 0 до 100
   решает, стоит ли сказать о бумаге;
2. **раз в неделю, по пятницам, присылает сигналы на покупку** — не больше пяти новых (из них не
   больше двух монет), только по бумагам, которых у вас нет, и не повторяя тикер, по которому
   сигнал уже был за последние 30 дней;
3. **следит за вашими позициями** — на счёте Trading 212 и записанными через `/bought` — и сразу,
   как сработало правило выхода, присылает сигнал на продажу.

Оценки — [model_score.py](model_score.py), дневной проход (`score_day`) — [model.py](model.py),
выбор недельных сигналов — [signals_weekly.py](signals_weekly.py), недельные сообщения и сводка —
[weekly.py](weekly.py), цены — [prices.py](prices.py). Таблицы `paper_*` остались в базе как архив
прежнего виртуального портфеля: ничего их не читает и не пишет.

Балл решает, говорить ли о бумаге; **волатильность** задаёт стоп; **выходы** — когда вам пора
продавать то, что у вас есть.

### Оценка акции

Акцию оценивают, только когда что-то произошло: сигнал покупки, раскрытый за
последние **14 дней**. Пока сигнал свежий, его пересчитывают каждый день — импульс и
новости меняются. Балл = инсайдеры + поводы + импульс + новости, от 0 до 100.

| Часть | Баллы | Из чего складывается |
|---|---|---|
| Инсайдеры | 0–60 | Руководство: 1 / 2 / 3 / 4+ покупателей → 22 / 34 / 42 / 46. CEO или CFO среди них +10 (председатель +5). Все их покупки от 0,01% / 0,05% / 0,2% стоимости компании +3 / +6 / +10. Позиция крупнейшего покупателя выросла на 10% / 30% и больше: +3 / +6. Первая покупка +4. Кластер из одних держателей >10% — ровно 15. Палата и Сенат здесь дают 0 — политики считаются в поводах |
| Крупная доля (13D/G) | вместо инсайдеров, до 60 | Активист 13D: 30 + 2 × (доля − 5), не больше 10 п.п. — от 30 до 50. Пассивный 13G: 15 + (доля − 5), не больше 10 п.п. +5, если доля выросла минимум на 1 п.п. Доля от 50% — 0 («контрольный пакет — не сигнал»: поглощение или материнская компания, а не ставка на цену). Поправка (13D/A, 13G/A) — 0 («поправка без роста доли»), если не видно роста минимум на 1 п.п. |
| Поводы | 0–20 | Активист 13D по тому же тикеру за 30 дней +15. Пассивный 13G от 10% +6. Считаются только первичные подачи (не поправки) с долей от 5% (13G — от 10%) и меньше 50%, а доля из сегодняшних кандидатов — только если сама набирает баллы. Покупают политики +5. Совпадение с независимым источником +5 (групповой выход по тикеру совпадением не считается) |
| Импульс | 0–15 | Доходность за 6 месяцев выше 0 → +5, выше +25% → +8. Цена выше 200-дневной средней +5. Доходность за месяц выше 0 → +2. Импульс никогда не блокирует покупку |
| Новости | −30…+10 | Заголовки за 14 дней. Негативные (downgrade, lawsuit, resigns, short seller …) −10 каждый, не ниже −30. Позитивные (upgrade, buyback, beats estimates, fda approval …) +5 каждый, не выше +10 |

**Красный флаг в заголовке блокирует покупку:** мошенничество (fraud, но не
anti-fraud), расследование SEC, повестка, going concern, банкротство, пересмотр
отчётности, делистинг и размещение акций (public/secondary offering, private placement,
at-the-market; IPO — не в счёт).

| Условие | Решение |
|---|---|
| Красный флаг в новостях | **блок** |
| 60 и больше, бумага торгуется | **покупка** |
| 60 и больше, не торгуется | наблюдение — с причиной |
| 45–59 | **наблюдение** |
| Ниже 45 | пропуск |

Акции, которой инсайдеры и поводы не дают дойти до наблюдения даже с полным импульсом
(15) и лучшими новостями (10) — меньше 20 баллов, — цены и новости не запрашиваются:
она сразу пропуск.

«Торгуется» — есть ряд цен (минимум 21 закрытие), капитализация от €20 млн и оборот
от €100 тыс в день (когда известны), и известен хотя бы один из двух размеров.
**Trading 212:** если бумаги нет у брокера, у сигнала на покупку стоит пометка «нет на
Trading 212» (в меню — «нет на T212») — решения она не меняет; без ключа (см. «Ключ Trading
212») пометки нет.

Почему такие веса: кластер из трёх руководителей с покупкой CEO на заметную долю
(42 + 10 + 3–6 + 3) набирает 58–61 ещё до импульса, то есть сигнал на покупку приходит и на просадке;
два директора на небольшие суммы (34) без импульса и хороших новостей не доходят и
до наблюдения; активисту 13D в одиночку (30–50) нужна поддержка; одни политики не
дойдут до сигнала на покупку никогда. Правила про поправки и контрольные пакеты — по
первому прогону на реальных данных: из 26 покупок большинство оказались рядовыми поправками
13D/A держателей, давно контролирующих компанию, и одно поглощение.

### Оценка монеты

Оцениваются тринадцать монет: BTC, ETH, SOL, XRP, BNB, DOGE, AVAX, HYPE, LTC, ENA, LINK, TRX,
SUI (`model.COINS`). Оценка одна на все: тренд, потоки и новости считаются для любой монеты
(потоки — те, что есть: приток в ETF — у BTC, ETH и SOL, покупки компаний — у всех), стоп — по
зажиму «крипто» (15–35%). Одна плохая цена не отменяет неделю: закрытие, которое не положительное
число (0, отрицательное, пустое), выбрасывается из ряда, а монета, чья оценка упала с ошибкой,
пишется в stderr и пропускается — остальные монеты, полнота дня и недельный выбор не страдают.

| Часть | Баллы | Из чего складывается |
|---|---|---|
| Тренд | 0–60 | Закрытие выше 100-дневной средней +15; каждая из доходностей за 20, 60 и 120 дней выше 0 — +15 |
| Потоки | −20…+15 | Бычий сигнал за 7 дней (приток в ETF, покупки компаний) +15. Медвежий сигнал, который подтверждает цена, −20 — это **осторожность** |
| Новости | −30…0 | Плохие заголовки — те же списки, что у акций: −10 каждый, не ниже −30. **Хорошие заголовки монете баллов не дают** («upgrade» в крипто-новостях — обновление сети, а не рейтинг: на живой проверке альты вырывались вперёд только из-за такого слова). Красные флаги — как у акций плюс «взлом», exploit, «украдено», иск SEC — по-прежнему блок |

**Покупка** — тренд вверх (закрытие выше 100-дневной средней и минимум две из трёх
доходностей выше 0), 60 баллов и больше, нет осторожности и красного флага.
Осторожность или красный флаг — **блок**, всё остальное — наблюдение. Монета, у которой
меньше 121 закрытия, — наблюдение с причиной «мало истории».

**Фильтр биткоина для альтов.** Альт (любая монета, кроме BTC и ETH) может получить решение
«покупка», только пока сам биткоин в восходящем положении: его закрытие выше 100-дневной
средней (`coin_trend(закрытия BTC)["above_ma100"]`, по завершённым дневным закрытиям). Иначе
решение альта — наблюдение с причиной «биткоин ниже 100-дн. средней — альты не покупаем»
(балл не меняется; блок остаётся блоком; причина добавляется, только когда без фильтра была бы
покупка). Если по биткоину нет истории (меньше 121 закрытия), он тоже не «вверх» — альты ждут, но
причина другая: «нет данных по биткоину — альты не покупаем». BTC и ETH фильтром не ограничены. Фильтр задаёт `btc_up` в `model_score.score_coin` (`None` —
без фильтра), применяет его `model._score_coins`.

### Стоп

- **Типичное движение** — средний модуль дневного изменения по последним 20 закрытиям.
- **Стоп** — 3 × типичное движение, но не уже 10% и не шире 25% для акций (15% и 35% для монет).
  Это расстояние от максимума, на котором бумагу пора продавать: оно названо в сигнале на покупку
  («стоп −10%») и фиксируется у вашей позиции при записи, по истории цен на тот момент: спокойную
  бумагу не выбьет обычный шум за месяцы инсайдерской ставки.
- **Размера позиции бот не считает**: покупать ли и на сколько, решаете вы.

### Выходы

Срабатывает первое из правил, и вам приходит сигнал на продажу вашей позиции (см. «Позиции»); сам
бот ничего не продаёт.

- **Акции:**
  1. **трейлинг-стоп** — закрытие на `stop_pct` и более ниже максимума с покупки;
  2. **причина ушла** — продал инсайдер из сигнала (Form 4 не по плану 10b5-1, Form 144,
     продажи в Осло/FI/BaFin) или активист по 13D/G сократил долю;
  3. **«стоит на месте»** — 60 рабочих дней в позиции и доходность ниже +5%;
  4. **год в позиции**;
  5. **красный флаг** в новостях по тикеру.
- **Монеты:** трейлинг-стоп; **тренд вниз** (закрытие ниже 100-дневной средней и
  доходность за 20 дней ниже 0); осторожность, подтверждённая ценой; красный флаг.

### Недельный ритм: сигналы и сводка по пятницам

**Когда и что приходит.** Сигналы недели выбирает утренний запуск пятницы (08:00), а уходят они в **пятницу в
17:00** отдельным лёгким запуском (`run_weekly.sh` → `python bot.py --weekly-send`, задание
`com.disclosurebot.friday`): он ничего не опрашивает и не оценивает заново, а берёт выбранные утром сигналы,
перечитывает цену и проверяет график каждого (`chart_check`: вердикт по фиксированным правилам бота, который
Claude сверяет с данными TradingView, новостями и календарём отчётов) — в блоке сигнала появляется строка
«Chart For / Neutral / Against». Если Claude не ответил, в блоке остаётся вердикт по правилам. Если в пятницу в 17:00 отправка не состоялась, сигналы уйдут с
обычным запуском субботы или воскресенья. Сумма в блоке — доля недельного бюджета (`/size budget 30`): бюджет
делится между сигналами по баллу, пропорционально баллу сверх 50 (сигнал с баллом 90 получает вчетверо больше
сигнала с баллом 60).

**Неделя** — первый полный (не отфильтрованный) прогон в пятницу, субботу или воскресенье
ISO-недели. Обычно это пятница; суббота или воскресенье — только если Mac пропустил пятницу.
Неделя помечается в `kv_cache` ключами:
`model_buys_<ГГГГ>-W<нн>` (покупки недели выбраны), `weekly_buys_<ГГГГ>-W<нн>` (JSON-список
выбранного — всё, что нужно сообщениям), `weekly_message_<ГГГГ>-W<нн>` (сигналы и сводка
отправлены; ставится после сводки — последнего сообщения недели) и
`weekly_sent_<ГГГГ>-W<нн>` (JSON-список сигналов недели, которые уже ушли).

**Каждый день** бот оценивает сигналы: оценки идут в журнал (колонка `tier`), в меню и к
аналитику. Ничего не покупается и не откладывается: оценка — это только оценка.

**Покупки недели выбираются один раз** — в недельном прогоне, когда оценки посчитаны полностью (без
упавшего прохода). Из оценок берутся только решения «покупка», по убыванию балла, и отсеиваются:

- бумаги, которых у вас уже есть, — открытая позиция из Trading 212 или `/bought` (монета — по
  тикеру `CRYPTO:`; бумага с биржи Осло или Стокгольма сравнивается вместе с биржей, так что
  норвежская NRC — не американская; бумага Trading 212, хранящаяся по ISIN норвежской компании,
  — это та же норвежская компания);
- тикеры, по которым сигнал на покупку уже приходил за последние 30 дней (`RESIGNAL_DAYS`,
  таблица `buy_signals`).

Остаётся не больше пяти новых (`WEEKLY_BUY_LIMIT`), и среди них не больше двух монет
(`WEEKLY_COIN_LIMIT`). Баллы монет и акций лежат на разных шкалах, поэтому места для монет
зарезервированы: сначала берутся до двух подходящих монет с решением «покупка»
(`signals_weekly.coin_priority`) — сначала BTC и ETH (`model.MAJOR_COINS`), какие бы баллы ни были у
альтов; затем альты по баллу, а при равных баллах — у кого выше доходность за 60 дней (`ret60` в
оценке монеты и в сохранённых оценках дня; нет значения — в конец). Остальные места (пять минус
взятые монеты) занимают акции с решением «покупка» по баллу: нет ни одной подходящей монеты — все
пять мест у акций; акций мало — выбранных меньше пяти, а не третья монета. Монета, которую
пропустили (она у вас есть, по ней уже слали сигнал за 30 дней или у неё не «покупка»), места не
занимает: нет BTC — место получает ETH, а второе — лучший альт. Порядок отправки один: сначала акции
по убыванию балла, затем монеты (BTC и ETH, потом альты). Строка покупки альта — любой монеты, кроме
BTC и ETH, — кончается словами «высокий риск»; пометка хранится в записи выбранного
(`weekly_buys_…`: поле `risk`), отдельного столбца в `buy_signals` нет. Выбранное сохраняется в
`weekly_buys_…` до отправки сообщений, и только потом ставится ключ `model_buys_…`: повторный
прогон окна пятница — воскресенье отправляет те же сигналы, не оценивая и не выбирая заново.

**Недельные сообщения** — по одному короткому сообщению на каждый сигнал недели и в конце короткая
сводка по вашему счёту; в тихую неделю приходит одна сводка. Порядок: сигналы на покупку (сначала
акции по убыванию балла, затем монеты: BTC и ETH, потом альты), групповые выходы — и сводка последней. Окно групповых выходов — семь дней, считая
сегодняшний. Сообщения ждут недельного выбора (ключ `model_buys_…`), а он — полного прохода оценок:
если в пятницу проход не состоялся или был неполным, ничего не уходит, а прогон субботы выбирает
покупки и присылает всё уже с ними. Исключение — воскресенье: сообщения уходят в любом случае, и
если оценка сигналов за неделю так и не отработала, последней строкой сводки стоит
«⚠️ Оценка сигналов на этой неделе не отработала — покупок не было.»

У каждого сигнала есть постоянный ключ: `buy:<тикер>`, `exit:<id записи журнала>`. Ключ попадает в
список недели (`weekly_sent_…`) только после того, как сообщение ушло, и в той же записи в базу:
строка `buy_signals` пишется после отправки своего сообщения — не раньше и не без ключа. Сигнал из
списка второй раз не шлётся. Если отправка упала на полпути, сводка не уходит, а неделя не
помечается (`weekly_message_…` ставится только после сводки): следующий прогон того же окна
пятница — воскресенье досылает только недостающее. Неделя, уже помеченная отправленной, не шлёт
ничего.

**Каждый день в Telegram приходит только** сигнал на продажу по тому, что вы отметили командой
`/bought` или держите на счёте Trading 212, — по одному сообщению на сигнал, сразу, как сработало
(это реальные деньги, ждать пятницы нельзя). Каждый сигнал помечается отправленным сразу после
своей отправки: если сообщение не ушло, оно и все после него придут в следующем прогоне. Кроме
них — сообщения о бумагах, появившихся на счёте Trading 212 или ушедших с него (см. «Trading
212»), и предупреждения о поломках (источник упал или молчит, оценка сигналов упала). Сигналы на
покупку и групповые выходы по дням не приходят: они в пятничных сообщениях.

В журнале сигналов колонка `tier` хранит решение модели за день (buy / watch / block /
skip) или `caution` для медвежьего сигнала по монете. Медвежьи сигналы записываются в
журнал до оценки дня, остальные — после: осторожность, найденная сегодня, считается сегодня (а по
монете, которая у вас в позиции, даёт сигнал на продажу). Оценки дня сохраняются (`kv_cache`,
`model_scored_<дата>`): меню, команда `portfolio` аналитика и его контекст по тикеру
берут их оттуда, а не считают всё заново.

### Как выглядят сообщения

**Сигнал на покупку** (по пятницам) — только сама сделка, блоком моноширинного шрифта: тикер и «Invest»,
цена (последнее закрытие), стоп, сумма в евро (`/size`), вердикт по графику одним словом («Chart For / Neutral
/ Against»); «Not on Trading 212», «High risk» (альт) и «Merger pending» — строки блока. Причины сигнала, балл,
строка о компании и текст проверки графика в сообщении не показываются — их даёт аналитик, если прислать тикер:

```none
GME Buy · Invest
Price 23.10
Stop  20.79
Size  €19
Not on Trading 212
```

```none
SOL Buy · Invest
Price 150.00
Stop  117.00
High risk
```

Без цены стоп — в процентах («Stop  -10%»); без баланса счёта нет строки Size.

Остальные автоматические сигналы — **одно короткое сообщение**: цветная точка, имя жирным с «!»,
что случилось, цена или подробности и — у сигнала на продажу — результат жирным. Вот по одному
примеру каждого вида (жирный шрифт здесь не виден):

```text
🔴 XYZ!: продают те, кто покупал — Anna Lee, Bo Chen
🔴 GME!: сработал стоп — пора продавать: вход 23,10 → сейчас 20,70, итог −$24,00 (−10,4%)
🔴 GME!: продаёт инсайдер — пора продавать: вход 23,10 → сейчас 20,70, итог −$24,00 (−10,4%)
   Ryan Cohen — Form 4, 01.10
⚪ GME!: куплено в Trading 212 — 10 шт. по 23,10 USD, слежу: стоп, продажи инсайдеров, новости
⚪ GME!: продано в Trading 212 — слежение закрыто, итог ≈ +$9,50 (+4,1%)
🟢 EURUSD!: вход в лонг (новый сигнал) — цена 1,2000, 200-дн. средняя 1,1500, спред DE-US 2 г. +0,35 п.п., стоп ~1,1520 (6×ATR)
⚪ EURUSD!: выход во флэт (сработал стоп) — цена 1,1600, выход ~1,1670
```

По порядку: сигнал на покупку; групповой выход; два сигнала на продажу вашей позиции (стоп —
одной строкой, продажа инсайдера — со второй); новая бумага на счёте Trading 212 и проданная;
вход и выход по EURUSD. Недельная сводка — последним сообщением недели:

```text
📊 Неделя 03.10–09.10: счёт Trading 212 €12 346 (за неделю +2,9%)
Позиций 43: лучшие — SMCI +31,0%, BBD +12,4%, GME +8,1%; худшие — XYZ −22,5%, ABC −9,0%, DEF −4,2%
Сигналов за неделю: покупок 2, на продажу 1, групповых выходов 1
⚠️ Оценка сигналов на этой неделе не отработала — покупок не было.
```

Последняя строка бывает только в неделю, когда оценка сигналов так и не отработала. Если данных
счёта нет, а позиций и сигналов не было, сводка короче:

```text
📊 Неделя 03.10–09.10
Позиций нет.
Сигналов за неделю не было.
```

Как читать:

- **Точка.** 🟢 — сигнал на покупку и сигнал на продажу с результатом от нуля; 🔴 — убыток (или
  результат неизвестен: у сигнала на продажу нет цены) и групповой выход; ⚪ — нейтральное
  событие: уведомления Trading 212 и выход во флэт по EURUSD, каким бы ни был итог. Вход по
  EURUSD — 🟢 в лонг и 🔴 в шорт.
- **Имя.** Монета — символом (`BTC`), бумага со счёта Trading 212 — так, как её знает владелец
  (`SAP`, а не ISIN), остальное — тикером. Числа — по-русски: `23,10`, `€10 000`, `+24,5%`, с
  настоящим минусом «−».
- **Покупка.** Не больше двух причин, балл и стоп; «нет на Trading 212», если у брокера бумаги
  нет. Суммы в сообщении нет: бот ничего не покупает, а сколько покупать, решаете вы.
- **Сигнал на продажу вашей позиции.** Что случилось, «пора продавать: вход X → сейчас Y» и итог. Для
  бумаги Trading 212 с известным количеством итог — деньги в валюте бумаги, а процент в скобках
  (`−$24,00 (−10,4%)`, `−€24,10 (−10,4%)` для бумаги в евро); для остального — процент. Без цены итога
  нет. Вторая строка — только у «продаёт инсайдер» (кто и когда), «отток по монете» (текст оттока)
  и «плохие новости» (заголовок); остальные сигналы — одна строка: главная строка уже всё говорит
  (стоп, срок, «стоит на месте», разворот тренда, сокращение доли активистом). В этой строке дата —
  `ДД.ММ` («Ryan Cohen — Form 4, 01.10»), а числа — по-русски: запятая в десятичных, пробел между
  тысячами, настоящий минус («−6,2%», «€1 050 млн»); заголовок новости — как есть, это чужой текст.
- **Групповой выход.** Первые пять имён, дальше «и ещё N».
- **Сводка.** Три строки про ваш реальный счёт, без обращения к сети — из того, что бот уже
  сохранил. Первая — неделя и счёт Trading 212 по последнему снимку не старше трёх дней (в
  скобках — изменение за неделю, если есть снимок недельной давности; без свежего снимка в строке
  только неделя). Вторая — сколько позиций открыто (со счёта Trading 212 и из `/bought`) и три лучших
  и три худших по результату с покупки: последняя сохранённая цена Trading 212 против цены входа;
  позиция без свежей (не старше трёх дней) цены и позиция из `/bought` (для неё бот цен не
  хранит) в рейтинг не входят, а при пяти и менее позициях с ценой все названы по одному разу,
  лучшая первой. Третья — сколько сигналов было за неделю: покупок (строки `buy_signals`), на
  продажу (позиции, по которым сигнал ушёл на этой неделе) и групповых выходов, или «Сигналов за
  неделю не было.» Предупреждение — четвёртая строка, только когда оценка сигналов так и не
  отработала.

### Как смотреть

- **Меню:** «1) Сигналы» — оценки модели; «3) Мой портфель» — то же, что `/portfolio` в Telegram,
  обычным текстом; «4) Спросить аналитика» (см. ниже).
- **Telegram:** `/portfolio` — ваши позиции: счёт Trading 212 и записанное через `/bought` (см.
  «Позиции» и «Trading 212»); любой тикер, вопрос текстом и `/ask` — как всегда. Сигналы на
  покупку и недельная сводка приходят по пятницам сами.

## Аналитик (TradingView)

Задайте вопрос — headless Claude ответит по данным бота (оценка модели, инсайдеры,
ваши позиции, новости, досье) и по **живому графику в вашем TradingView Desktop**.
Код — [analyst.py](analyst.py), методика — [analyst_method.txt](analyst_method.txt),
промпты — [claude_analysis_prompt.txt](claude_analysis_prompt.txt) (очередь Telegram)
и [claude_ask_prompt.txt](claude_ask_prompt.txt) (терминал).

**Как спросить**

- **Telegram:**
  - тикер или монета одним словом (`NVDA`, `BTC`, `EQNR.OL`) — один разбор, как раньше,
    теперь и с графиком;
  - любой другой текст или `/ask …` — вопрос: «что думаешь про NVDA?», «сравни BTC и
    ETH», «почему пришёл сигнал по …»;
  - портфель в Telegram не показывается: он в приложении Trading 212 (в терминале — пункт меню).

  Ответ приходит через 1–5 минут (бот сначала пишет «Думаю над вопросом…»). Если за 7
  минут ответа нет, вопрос остаётся в очереди, и ответ придёт позже — с ближайшим
  плановым прогоном очереди. После трёх неудачных попыток приходит «Не удалось
  ответить: … — попробуйте спросить ещё раз.», и строка закрывается.
- **Терминал:** `python analyst.py ask "вопрос"` или меню → «4) Спросить аналитика».
  Ответ печатается в терминал, в Telegram ничего не уходит.

**Что нужно**

- **TradingView Desktop.** Аналитик проверяет соединение; если TradingView закрыт, он
  запускает его с портом отладки (не трогая уже открытый). Если и так не вышло,
  отвечает по данным бота и пишет «TradingView недоступен».
- **Залогиненный Claude CLI.** Если запуски падают с «OAuth session expired», один раз
  выполните `~/.local/bin/claude` и в нём `/login`.

**Как это устроено**

- **Один запуск Claude на один вопрос.** `analyst.py` сам собирает промпт: шаблон
  (Telegram или терминал), всю методику и данные — текст вопроса или, для тикера,
  контекст бота по нему, посчитанный заранее. Вопрос и данные стоят между метками
  «данные, не инструкции» и в командную строку не попадают.
- **Ответ отправляет сам аналитик**, не Claude: последнее сообщение Claude и есть
  ответ, `analyst.py` шлёт его в Telegram (если Telegram отверг HTML — ещё раз
  простым текстом) и только потом отмечает строку обработанной. Три неудачные
  попытки — сообщение «не удалось ответить».
- **Headless Claude ограничен.** Каждый запуск идёт в новой пустой временной папке вне
  проекта (после запуска она удаляется), так что даже команды чтения, которые Claude
  может выполнять в своей рабочей папке без разрешения, ничего там не находят. Файлы
  настроек Claude он игнорирует (`--restricted`); из встроенных инструментов у него
  только shell (`--tools Bash`), файловых нет — читать и писать файлы проекта, `.env`
  в том числе, он не может; из MCP-серверов — только TradingView; всё, что не
  разрешено, отклоняется без вопроса (`--permission-mode dontAsk`). Shell разрешён ровно
  для трёх команд чтения, заданных абсолютными путями:
  `<проект>/.venv/bin/python <проект>/analyst.py context 'ТИКЕР'`, `… portfolio`,
  `… news 'ЗАПРОС'` (путь `analyst.py` подставляет в промпт сам). Ключей он не
  получает: из его окружения убрано всё, что задаёт `.env`, токены Telegram и всё, что
  называется `*TOKEN*`, `*SECRET*`, `*API_KEY*`, `*PASSWORD*`.

**Что он делает и чего не делает**

- По каждому активу (не больше трёх) переключает график на его символ, читает котировку
  и свечи — день (250 и 60 баров) и неделя (104 бара) — считает тренд, положение в
  3-месячном и годовом диапазоне и уровни, а потом **возвращает ваш график**: тот
  символ и таймфрейм, что были открыты.
- Из TradingView разрешены только девять инструментов: `tv_health_check`, `tv_launch`,
  `chart_get_state`, `chart_set_symbol`, `chart_set_timeframe`, `quote_get`,
  `data_get_ohlcv`, `symbol_info`, `symbol_search`. Индикаторы, рисунки, алерты, Pine,
  replay, раскладки и `data_get_study_values` (он выдаёт ваши приватные скрипты) ему
  недоступны.
- Команда `portfolio` печатает сперва ваши позиции из `/bought` (вход, цена и результат,
  стоп, за кем следит бот), потом «СИГНАЛЫ НА ПОКУПКУ ЗА 30 ДНЕЙ» (дата, тикер и балл — из
  `buy_signals`, новые первыми) и «НАБЛЮДЕНИЕ» (оценки с решением «наблюдение», до десяти):
  вопрос про «мои позиции» или про то, что бот присылал, запускает её. Если бот следит за
  счётом Trading 212, раздел начинается со счёта — последний сохранённый снимок и каждая
  бумага с количеством, средней ценой, последней сохранённой ценой и результатом. Это
  только сохранённые данные: к Trading 212 аналитик не обращается. Аналитик знает, что бот не
  ведёт портфель: он оценивает сигналы, а единственный портфель — ваш счёт.
- Команда `context 'ТИКЕР'` берёт оценку из сегодняшних сохранённых оценок, а если там этого
  тикера нет — считает заново и **только то, что нужно** (`model.score_today(…, coins=…)`): для
  акции — без монет (ни цен, ни новостей по монетам), для монеты — её одну; для альта ещё
  читаются цены биткоина, но только для фильтра биткоина (самого биткоина в оценках нет, если
  спрашивали не про него). `$BTC` — это акция, монеты он не считает. Меню и `portfolio` считают
  все тринадцать монет (`coins=None`).
- Уровни цен — только из TradingView или бота, выдуманных нет. Ответ — по-русски,
  коротко, с оценкой модели и одной строкой «🎯 Итоговый вердикт».
- Одновременно работает один Claude (замок `data/analyst.lock` общий у очереди и
  терминала: вопрос из терминала ждёт до 10 минут, потом «аналитик занят другим
  вопросом — попробуйте позже»). Один запуск Claude — не дольше 15 минут.

## Тесты

```bash
source .venv/bin/activate
pytest tests/ -q
```

Тесты офлайновые: парсеры проверяются на **сохранённых реальных** ответах
источников (`tests/fixtures/`), а логика сигналов — на SQLite в памяти. Сеть не
нужна, поэтому прогон занимает секунды и не падает от того, что источник лёг. Это
не только соглашение: `tests/conftest.py` отказывает любому соединению (и через
`socket`, и через `curl_cffi`, на котором работает yfinance), так что тест, который
тихо ходит в сеть, упадёт сразу.

Смысл именно в парсерах: каждый из них читает формат, который никто не обещал не
менять, — XML (причём 13D и 13G с разными именами полей), PDF по координатам слов,
HTML-таблицу по номерам колонок, свободную прозу регуляркой и CSV в UTF-16 с
десятичной запятой. Когда такой формат меняется, парсер **не падает** — он
возвращает пустоту, что неотличимо от «на рынке тихо». Тесты ловят это заранее,
а `--silent-source-runs` (см. ниже) ловит это в бою.

Остальное покрытие — регрессии на конкретные ошибки: повтор сигнала при новом
участнике, повтор одиночной покупки при росте суммы, имена с запятыми
(«CASCADE INVESTMENT, L.L.C.»), мусорный тикер `NONE`, сопоставление одного
человека между Form 4 и Form 144 («CHEN SEAN» ↔ «Sean Chen»), докат пропущенных
дней и определение молчащего источника.

### Позиции

Команды Telegram-бота для того, что вы реально купили:

- `/bought TICKER [цена]` — отметить покупку; без цены берётся последнее закрытие.
  Примеры: `/bought GME 23.10`, `/bought BTC` (монета; так же любая из тринадцати: `/bought HYPE 90`),
  `/bought EQNR.OL`. Акции Осло и
  Стокгольма пишутся как на Yahoo (`EQNR.OL`, `VOLV-B.ST`): бот хранит их так, как их знают
  таблицы сигналов, — тикер без суффикса и источник (`EQNR`, `NORWAY`), — и берёт цену на
  своей бирже, а не у одноимённой американской бумаги. У акций Стокгольма сигналы
  Finansinspektionen идут по ISIN, поэтому за продажами инсайдеров такая позиция не
  следит (стоп, срок и новости работают).
- `/sold TICKER` — отметить продажу (`/sold EQNR.OL` или `/sold EQNR`).
- `/portfolio` (или `/positions`) — **ваши позиции**, каждая с текущим состоянием: вход и
  дата, цена и результат, стоп и расстояние до него и за чьими продажами следит бот; внизу —
  средний результат. Первым идёт счёт Trading 212, запрошенный в этот момент (см. «Trading
  212»), ниже — записанное через `/bought`. Без Claude: цены берутся у Trading 212 и с Yahoo,
  так что ответ приходит через несколько секунд.

То, что лежит на счёте Trading 212, бот видит сам (см. «Trading 212») — `/bought` нужен только
для остального. Счётом бот не торгует: он его только читает. Позиция выходит по правилам
из раздела «Выходы»; стоп фиксируется при записи, по истории цен на тот момент
(«стоп −N% от максимума» в ответе бота).

Сигнал на продажу приходит один раз, по первому из: продаёт кто-то из инсайдеров, давших
сигнал (Form 4 не по плану 10b5-1, Form 144, продажи в Осло/FI/BaFin); для монеты —
осторожность за последние 7 дней (не раньше открытия позиции), подтверждённая ценой;
сработал трейлинг-стоп; для позиции, открытой на доле 13D/G, — активист сократил долю;
монета в тренде вниз; акция «стоит на месте» (60
рабочих дней и меньше +5%); прошёл год; красный флаг в новостях. Позиция закрывается
только командой `/sold` — а позиция со счёта Trading 212 закрывается сама, когда бумаги
на счёте больше нет.

### Trading 212

Бот **читает** ваш счёт Trading 212 и сам следит за тем, что на нём лежит, — без `/bought`.
Это только чтение: бот **никогда не размещает, не меняет и не отменяет заявки**. Кода для
этого в проекте нет; что именно проверяют тесты — в конце раздела. Код —
[t212_account.py](t212_account.py).

**Что читается.** Два запроса публичного API (v0), оба `GET`:

- `/equity/positions` — открытые позиции: инструмент, количество, средняя цена покупки,
  текущая цена, результат в валюте счёта;
- `/equity/account/summary` — сводка счёта: стоимость, свободные деньги, сколько вложено,
  результат.

Третий адрес — список инструментов (`/equity/metadata/instruments`) для пометки «нет на
T212». Больше бот к Trading 212 не обращается никуда.

**Как часто.** Каждые 15 минут — в постоянно работающем Telegram-боте (первая синхронизация
сразу при запуске; после сна Mac — сразу, как проснулся) — и ещё раз в ежедневном прогоне,
прямо перед проверкой выходов (в отфильтрованном прогоне — нет). Сбой API ничего не
меняет: всё записывается одной транзакцией и только когда оба запроса прошли, так что
ложное «продано» из-за ошибки не появится. Ошибка синхронизации в Telegram-боте пишется в
лог, и бот продолжает отвечать.

**Если Trading 212 перестал отвечать.** Молча это не останется:

- если синхронизация раньше проходила, а теперь не проходит уже сутки, раз в день приходит
  «⚠️ Trading 212 не отвечает уже сутки (причина): позиции не обновляются.» Это про ошибки
  API: ключ не подходит, не хватает прав, сеть, сбой сервера — и про сбой самой синхронизации
  (ошибка при записи в базу или при разборе счёта: в причине её тип, без текста). Предупреждение
  помечается в базе до отправки: заблокированная база или сбой записи отметки не приведут к
  тому, что оно будет приходить при каждой синхронизации;
- если ключ убран из `.env` — это не сбой, а ваше решение. Бот один раз пишет «Ключ Trading
  212 убран — слежение за счётом остановлено. Позиции из Trading 212 остаются в /portfolio
  по последним данным.» и больше не напоминает, пока ключ не появится снова. Ключ процесс
  берёт из своего окружения, а если там его нет — из `.env`: Telegram-бот живёт с ключом, с
  которым был запущен, и синхронизируется и после того, как ключ убран из `.env`, а ежедневный
  прогон читает `.env` заново. Поэтому «убран» бот не говорит, пока хоть одна синхронизация
  (любого процесса) прошла за последний час, а отметку «сказано» снимает только процесс,
  который сам был без ключа. Поменяли или убрали ключ в `.env` — перезапустите Telegram-бота
  (команда — ниже, в «Ключ Trading 212»);
- если список позиций не сходится со сводкой счёта уже сутки (а раньше сходился), раз в день
  приходит «⚠️ Trading 212: список позиций не сходится со счётом уже сутки — продажи не
  отмечаю.» Позиции при этом открываются и обновляются, но проданные не закрываются;
  расхождение покажет `python t212_account.py --check`;
- после ошибки ключа (401, 403) бот повторяет попытку раз в час, а не каждые 15 минут;
- сохранённая цена старше трёх дней ценой не считается: стоп по ней не проверяется (как при
  «цена недоступна»), а `/portfolio` показывает её как «цена на ДД.ММ: …»;
- счёта в первой строке пятничной сводки («счёт Trading 212 €X …») нет, если последний
  снимок счёта старше трёх дней; цена бумаги старше трёх дней в рейтинге позиций сводки тоже
  не участвует.

**Что делает синхронизация.**

- **Новая бумага на счёте** становится позицией бота, как после `/bought`: вход — средняя
  цена Trading 212, дата — когда позиция открыта там, стоп — по истории цен, инсайдеры — из
  журнала сигналов. Дальше работают те же правила выхода (стоп, продажи инсайдеров, срок,
  новости) и тот же сигнал на продажу.
  - Американская бумага (`AAPL_US_EQ` → `AAPL`, `BRK_B_US_EQ` → `BRK.B`) оценивается по
    дневным закрытиям Yahoo, как позиция из `/bought`. Коды Trading 212 у каждой пятой
    американской бумаги устаревшие (`FB_US_EQ` — это Meta), поэтому тикер берётся из списка
    инструментов Trading 212 (`META`), а если бумаги в списке нет — из самого кода. При
    открытии позиции цена проверяется: если у Yahoo под этим тикером есть история и её
    последнее закрытие расходится с ценой Trading 212 больше чем на 20%, это не та бумага —
    позиция хранится по ISIN и оценивается по ценам Trading 212, как европейская. Если Yahoo
    не ответил или не знает тикер, бумага остаётся под своим тикером — со своими инсайдерами и
    новостями.
  - Цена для стопа у любой позиции со счёта: закрытия Yahoo, когда они у Yahoo есть, иначе —
    цены самого Trading 212, которые бот записывает раз в день. Так что бумага, которой Yahoo
    не знает или по которой не отвечает, всё равно оценивается, и её стоп работает. Если Yahoo
    потом начал отвечать по старому коду бумаги, а его последнее закрытие расходится с
    сохранённой свежей ценой Trading 212 больше чем на 20%, это серия другой бумаги: стоп
    считается по ценам Trading 212, а не по ней.
  - Любая другая (Франкфурт, Лондон, Амстердам…) хранится по ISIN и оценивается по ценам
    самого Trading 212: бот записывает цену каждой бумаги раз в день (последняя за день).
    Инсайдеры ищутся по ISIN (так их называют BaFin и Finansinspektionen), а для компании с
    биржи Осло — ещё и по её тикеру в Осло; там же читаются её новости. У остальных бумаг,
    которые хранятся по ISIN, выхода по новостям нет — у ISIN нет новостной ленты (как и у
    позиции `/bought` по ISIN); стоп, продажи инсайдеров и срок работают.
- **Докупили или продали часть** — количество и средняя цена обновляются, без сообщения.
- **Бумага уже записана через `/bought`** — позиция переходит под Trading 212 (количество и
  вход берутся со счёта), без сообщения. Только если это та же самая бумага: американская
  бумага со счёта не забирает позицию, записанную на бирже Осло или Стокгольма под теми же
  буквами (`EQNR` в Нью-Йорке — не `EQNR.OL`), а ведётся рядом, по ISIN.
- **Бумаги больше нет на счёте** — позиция закрывается с причиной «продано в Trading 212».
  Но только когда списку позиций можно верить: сумма стоимости бумаг в нём должна сходиться с
  «вложено» из сводки счёта той же синхронизации (с точностью 2% или €5).
  - Пустой список, когда во вложениях больше €5, — плохой ответ: ничего не меняется. Остаток
    в несколько центов после продажи всего — это пустой счёт: позиции закрываются.
  - Список, который не сходится со сводкой (пришёл не целиком), открывает и обновляет позиции,
    но ни одной не закрывает.
  - Если список нельзя сверить со сводкой — в сводке нет суммы вложений, у бумаги нет своей
    стоимости или стоимость бумаг в списке дана в другой валюте, чем в сводке, — продажа
    подтверждается второй синхронизацией подряд, не раньше чем через 10 минут после первой
    (ежедневный прогон и Telegram-бот — разные процессы, и две синхронизации с разницей в
    секунды могут встретить один и тот же плохой ответ).
- **Бумага пропала и вернулась** (тот же инструмент и та же дата покупки в Trading 212) —
  позиция восстанавливается как была: с прежней датой начала слежения, стопом и инсайдерами,
  без нового сообщения «куплено в Trading 212».
- Раз в день сохраняется и снимок счёта: из него первая строка пятничной сводки («📊 Неделя
  …: счёт Trading 212 €X (за неделю ±Y%)») и раздел «ВАШИ ПОЗИЦИИ (Trading 212 и /bought)» у
  аналитика (аналитик читает только сохранённое, сам к Trading 212 не обращается). Из
  сохранённых цен бумаг — результаты позиций во второй строке сводки.

**Бумаги, купленные до подключения счёта.** То, что уже лежало на счёте, когда бот увидел
его в первый раз, не должно завалить вас сигналами на продажу в первый же день. Для таких
бумаг правила выхода считаются со дня первой синхронизации, а не со дня покупки:

- год в позиции и «стоит на месте» (60 рабочих дней и меньше +5%) отсчитываются от первой
  синхронизации;
- стоп считается от цены на день первой синхронизации (и от закрытий после неё), а не от
  средней цены покупки: бумага, которая давно в минусе, не выбивается стопом в первый день.
  Ширина стопа — как обычно, по истории цен до этого дня;
- результат при этом показывается настоящий — от средней цены покупки в Trading 212, — и
  число дней в `/portfolio` считается от даты покупки там.

Бумага, которая появилась на счёте уже после первой синхронизации, — обычная новая позиция:
вход по средней цене, дата — день покупки в Trading 212, стоп — от цены входа.

**Сообщения в Telegram.**

- первая синхронизация — одно сообщение на всё: «📥 Слежу за вашими позициями в Trading 212
  (N): GME, INBX, …», и второй строкой — «Для уже купленных бумаг правила выхода считаются с
  сегодняшнего дня.»;
- новая бумага — «⚪ GME!: куплено в Trading 212 — 10 шт. по 23,10 USD, слежу: стоп, продажи
  инсайдеров, новости». Сообщение называет только то, за чем бот для этой бумаги
  действительно следит. «Продажи инсайдеров» — только если в журнале сигналов есть её
  инсайдеры (у американской — по тикеру, у BaFin и Finansinspektionen — по ISIN, у Осло — по
  тикеру Осло). Американская бумага без инсайдеров — «слежу: стоп, срок и новости». Для
  бумаги, которая хранится по ISIN, новостной ленты нет — «слежу: стоп и срок», с
  инсайдерами — «…, а также продажи инсайдеров», у компании с биржи Осло — «…, а также
  новости»;
- бумага продана — «⚪ GME!: продано в Trading 212 — слежение закрыто». Когда известны средняя
  цена и свежая (не старше трёх дней) цена, которую синхронизация сохранила в последний раз,
  в конце добавляется «, итог ≈ +$9,50 (+4,1%)»: деньги в валюте бумаги, если известно
  количество, иначе процент; «≈» — потому что это не цена, по которой продали. Точка у всех
  этих сообщений белая, каким бы ни был итог.

**`/portfolio` — живой.** Команда обращается к Trading 212 в момент вызова и начинает ответ
с «💼 Trading 212»:

- строка счёта — «Счёт: €X · вложено €Y · P/L ±€Z (±W%) · свободно €C»;
- по блоку на бумагу — «• GME — 10 шт., средняя 23,10, сейчас 24,05 USD (+4,1%), €+8,30,
  5 дн.» (результат — от средней цены покупки, дни — от даты покупки в Trading 212, если она
  известна), под ней стоп и расстояние до него и за чьими продажами следит бот;
- ниже, под «✍️ Вне Trading 212», — то, что записано через `/bought`; внизу — средний
  результат по всем позициям.

Если Trading 212 не ответил, показываются сохранённые данные с пометкой «⚠️ Trading 212 не
ответил (причина) — данные на ЧЧ:ММ последней синхронизации». Если ключа нет или ему не
хватает прав, вместо счёта — причина и подсказка, какой ключ создать.

`/bought X` для бумаги со счёта отвечает «X уже отслеживается из Trading 212.», а `/sold X`
— «X отслеживается из Trading 212: продайте там — бот увидит продажу сам.» X — тикер
позиции или код американской бумаги в Trading 212 (Meta бот ведёт как `META`, а в Trading
212 её код — `FB`: подойдут оба). Бумагу, которая хранится по ISIN, называет только её ISIN:
`SAP` в Telegram — это американская SAP, а не франкфуртская (сотни неамериканских бумаг носят
тикер американской компании).

**Проверка ключа.**

```bash
python t212_account.py --check   # «Trading 212: доступ есть, позиций N, валюта EUR» или причина
python t212_account.py --sync    # одна синхронизация сейчас, без сообщений в Telegram
```

Второй строкой `--check` печатает, как бот разберёт позиции: «Ключи: США — 7, ISIN — 5; с
ценой — 12 из 12; список и сводка сходятся». Последнее важно: продажа признаётся, только
когда список позиций сходится со сводкой счёта. Если здесь стоит «расходятся на N%», бот
будет открывать и обновлять позиции, но не закрывать проданные.

`--check` не печатает ничего, что идентифицирует счёт (ни номера, ни сумм, ни бумаг), и
никогда — ключ. `--sync` (как и прогон `bot.py --no-telegram`) ничего не отправляет и не
расходует первое общее сообщение: его пришлёт первая синхронизация, которая может писать в
Telegram, и перечислит в нём все бумаги, за которыми бот уже следит.

**Почему бот не торгует.** Главная защита — ключ без прав на заявки (см. «Ключ Trading
212»): таким ключом заявку не разместить, что бы ни было в коде и даже если ключ утечёт.

Вторая — тесты (`tests/test_t212_account.py`). Это проверка текста исходников и поведения
клиента, а не доказательство невозможности. Они проверяют, что:

- в `t212_account.py` и `trading212.py` нет вызовов `.post(`, `.put(`, `.patch(`,
  `.delete(`, `.request(`, `.send(`, `getattr(` и `__import__(`, нет импорта сетевых
  библиотек, кроме `requests`, нет адресов Trading 212, кроме трёх перечисленных выше, и нет
  путей с `/orders`;
- адрес Trading 212, функция, собирающая заголовок авторизации, и имена переменных ключа
  упоминаются только в этих двух модулях — больше нигде в коде проекта;
- клиент, синхронизация и `/portfolio` на сессии-заглушке вызывают только `get` и только по
  этим трём адресам.

Ключ, секрет и заголовок авторизации не попадают ни в логи, ни в тексты ошибок.

**Сплит акций.** Для любой бумаги, которая оценивается по ценам Trading 212 — хранится по
ISIN или американская, по которой у Yahoo нет данных (или они чужие), — сплит выглядит как
резкое падение цены: может прийти одно ложное сообщение «пора продавать» по стопу.

### Ключ Trading 212

Нужен для двух вещей: слежения за счётом (см. «Trading 212») и пометки «нет на Trading 212»
у сигналов на покупку. Без ключа ни того, ни другого просто нет. В приложении или на сайте
Trading 212: ☰ → Settings → API (Beta) → Generate API key. Разрешения — **только чтение**:

- **Metadata** — список инструментов (пометка «нет на T212»);
- **Portfolio** — открытые позиции;
- **Account data** — сводка счёта.

Разрешения на заявки (Orders…) и «пироги» (Pies…) **не включайте**: боту они не нужны, а
ключ без них не может торговать. Можно ограничить ключ своим IP. Секрет показывается один
раз. Оба значения — в `.env`:

```
TRADING212_API_KEY="..."
TRADING212_API_SECRET="..."
```

Проверить ключ: `python t212_account.py --check`. API доступен для счетов Invest и Stocks
ISA.

Поменяли или убрали ключ в `.env` — перезапустите Telegram-бота, он держит прежний ключ в своём
окружении: `launchctl kickstart -k gui/$(id -u)/com.disclosurebot.telegram`.

Бэктест и оценка модели в меню не показываются — они запускаются отдельно:
`python backtest.py`, `python model_eval.py`. Отчёт по конкретному политику —
`python politician_report.py` (см. раздел ниже).

## Рейтинг конгрессменов по доходности

House PTR не публикует ни цену покупки, ни число акций — только сумму-вилку
(например «$50,001 - $100,000»). Поэтому доходность — **оценка**, не точный
P&L: берётся цена закрытия тикера на дату сделки и текущая цена, доходность в
% считается по их отношению, а «прибыль в $» — как середина вилки суммы,
умноженная на эту доходность. Игнорирует, была ли позиция реально продана,
дивиденды и т.п. — это сигнал для ранжирования, а не бухгалтерия.

Логика — [congress_score.py](congress_score.py) (`LOOKBACK_MONTHS` — окно в
12 месяцев по умолчанию). Исторические цены кэшируются в SQLite навсегда
(`price_history_cache` — цена закрытия в прошлом не меняется), текущая цена —
каждый раз заново.

## Разовая настройка

Требуется **Python 3.12+** (см. `.python-version`). Системный `python3` на macOS —
это 3.9, который снят с поддержки; не используйте его.

```bash
cd ~/Desktop/disclosure-bot

# вариант с uv (рекомендуется — сам скачает нужный Python)
uv venv --python 3.12 && uv pip install -r requirements.lock

# либо, если Python 3.12 уже установлен
python3.12 -m venv .venv && .venv/bin/pip install -r requirements.lock

cp .env.example .env   # уже сделано, но если пересоздаёте — не забудьте
```

`requirements.lock` — закреплённые версии, проверенные в работе (28 пакетов,
Python 3.12.14). `requirements.txt` — только прямые зависимости без версий;
установка из него подтянет свежие мажорные версии и может всё сломать.

Откройте `.env` и впишите два значения (это единственное, что обязательно):

### 1. `TELEGRAM_BOT_TOKEN`

1. Откройте Telegram, найдите **@BotFather** (это официальный бот Telegram для
   создания ботов).
2. Отправьте ему `/newbot`.
3. Он спросит имя бота (любое, например `My Disclosure Bot`) и username
   (должен заканчиваться на `bot`, например `my_disclosure_alert_bot`).
4. В ответ пришлёт токен вида `123456789:AAExampleTokenReplaceMe` — это и есть
   `TELEGRAM_BOT_TOKEN`. Проверить, что токен рабочий, можно так:
   `curl "https://api.telegram.org/bot<ТОКЕН>/getMe"` → должно вернуть
   `{"ok":true,...}` (не `404`).

### 2. `TELEGRAM_CHAT_ID`

1. Найдите своего только что созданного бота в Telegram (по username, который
   вы ему дали) и отправьте ему **любое сообщение** (например `/start`) — это
   обязательный шаг, иначе бот не сможет писать вам первым.
2. Откройте в браузере (подставив свой токен):
   ```
   https://api.telegram.org/bot<TOKEN>/getUpdates
   ```
3. В JSON-ответе найдите `result[0].message.chat.id` — это число (может быть
   отрицательным, если это группа, а не личный чат) и есть `TELEGRAM_CHAT_ID`.
4. Если ответ пустой (`"result":[]`) — значит сообщение боту ещё не дошло,
   отправьте его ещё раз и обновите страницу.

`SEC_USER_AGENT` — **настоятельно рекомендуется задать**. Раньше это было
необязательно, но SEC теперь троттлит общий плейсхолдер: запросы к дневному
индексу начинают отвечать HTTP 503, и день просто не сканируется (бот это
переживёт — оставит день на следующий прогон, — но данные будут отставать).
Впишите строку вида `SEC_USER_AGENT="MyDisclosureBot ваш-email@example.com"`;
политика SEC fair-access просит именно реальный контакт.

Без Telegram-значений бот всё равно работает — просто пропускает отправку
(пишет предупреждение в лог, не падает).

## Ежедневный автозапуск

### ⚠️ Обязательный шаг: Full Disk Access

Без него автозапуск **не работает вообще**. Так и было: c 27.08 по 08.09 задача
падала каждое утро, и никто об этом не знал —

```
$ launchctl list | grep disclosure
-	126	com.disclosurebot.daily          # 126 = не смогли выполнить
$ tail -1 data/launchd.err.log
/bin/bash: /Users/.../disclosure-bot/run_daily.sh: Operation not permitted
```

Причина — macOS TCC: процесс, запущенный из launchd, не может читать `~/Desktop`,
пока исполняемому файлу не выдан Full Disk Access. Проект лежит на Рабочем столе,
`ProgramArguments` начинается с `/bin/bash` — значит, разрешение нужно именно
`/bin/bash`.

**Системные настройки → Конфиденциальность и безопасность → Полный доступ к
диску → «+» → ⌘⇧G → `/bin/bash` → включить.**

Учтите цену: это даёт доступ к защищённым папкам **любому** bash-скрипту на
машине. Альтернатива без такого расширения прав — перенести проект из `~/Desktop`
(например в `~/disclosure-bot`), тогда разрешение не нужно совсем; надо будет
поправить пути в plist и в `~/.local/bin/disclosurebot`.

Проверка, что всё встало:

```bash
launchctl start com.disclosurebot.daily && sleep 10
launchctl list | grep disclosure     # во второй колонке должен быть 0, а не 126
tail -20 data/bot.log
```

### Опинион + чтение новостей headless-агентом Claude (`claude-analysis`)

`opinion.py` детерминированный и не читает новости содержательно (только грубый
keyword-подсчёт, см. его же дисклеймер). Настоящее чтение заголовков требует
реального рассуждения — либо спросить Claude напрямую в сессии, либо вот эта
задача, которая делает то же самое по расписанию.

**Почему не облачный агент.** Рассматривался `/schedule` (облачный routine) —
у него **нет доступа** к локальной файловой системе, локальной SQLite-базе и
`.env` с токеном Telegram-бота (подтверждено документацией самого скилла). Дать
ему токен означало бы держать боевой Telegram-токен в облачной конфигурации
навсегда — принято решение не делать так, и вместо этого используется локальный
headless-запуск `claude -p` тем же способом, что и остальные задачи здесь: без
отдельного API-ключа, доступ к БД/`.env`/`opinion.py` как у любого другого
локального скрипта.

**Как это работает:**
1. `telegram_bot.py` кладёт в очередь `claude_analysis_queue` тикер
   (`db.enqueue_analysis`, с дедупликацией по ещё-не-обработанным строкам) или
   вопрос (`db.enqueue_question`, без дедупликации) и **сразу же, синхронно**,
   запускает `run_claude_analysis.sh` сам — не дожидаясь планового запуска по
   расписанию. Тикер объединён в один ответ по просьбе пользователя (было два
   сообщения: быстрый `opinion.py`-ответ сразу плюс качественный разбор позже) — он
   явно принял задержку ради цельного ответа. Синхронный прогон ограничен 420
   секундами и идёт в собственной группе процессов: по таймауту бот шлёт группе
   SIGTERM (`analyst.py` по нему останавливает и свой Claude), через 15 секунд —
   SIGKILL. Успех бот определяет не по коду выхода, а по своей строке: если после
   прогона она не отмечена обработанной (прогон не уложился, упал или не дошёл до
   неё), для тикера бот откатывается на быстрый `opinion.py`-ответ, а для вопроса пишет
   «Не успел ответить — вопрос в очереди, ответ придёт позже». Отредактированное
   сообщение в Telegram новым запросом не считается.
2. Раз в 30 минут `run_claude_analysis.sh` запускается и по расписанию (ловит то, что
   синхронный триггер пропустил — сбой, восстановление после простоя). Он делает
   `python analyst.py process-queue`: пустая очередь — выход сразу, без запуска
   Claude; иначе — по одному headless `claude -p` на каждую строку (до 10 за прогон),
   ограниченному так, как описано в «Аналитик (TradingView)»: в пустой временной папке
   вне проекта, без файлов настроек, без файловых инструментов, без ключей, shell —
   только три команды чтения `analyst.py` по абсолютным путям, плюс девять инструментов
   TradingView. Замок `data/analyst.lock` не
   даёт плановому и синхронному прогонам ответить на одни строки дважды, а запуск
   Claude дольше 15 минут останавливается (и прогон на этом заканчивается).
3. Промпт каждой строки `analyst.py` собирает сам: шаблон
   [claude_analysis_prompt.txt](claude_analysis_prompt.txt), методику
   [analyst_method.txt](analyst_method.txt) и данные строки — текст вопроса или контекст
   бота по тикеру (оценка модели, позиции, досье с балансом `opinion.py`, вход/цель,
   заголовки), посчитанный до запуска. Claude читает график в TradingView и отвечает
   ОДНИМ сообщением с итоговым вердиктом. Ни тикер, ни вопрос в shell-команду не
   подставляются никогда (очередь хранит `$NVDA`, а внутри двойных кавычек shell
   превратил бы его в пустую строку).
4. Последнее сообщение Claude — это ответ: `analyst.py` отправляет его в Telegram
   (при отказе Telegram из-за HTML — ещё раз простым текстом) и отмечает строку
   обработанной только после подтверждённой отправки. Неудачный запуск (ошибка, пустой
   ответ, таймаут, обе отправки не прошли) считается попыткой; строка ждёт следующего
   прогона, а после трёх попыток приходит «Не удалось ответить: … — попробуйте спросить
   ещё раз.», и строка закрывается.

**Промпт живёт в отдельном файле, не инлайном в скрипте**: `/bin/bash` на этой
машине — древняя сборка Apple 3.2, у которой апостроф внутри `<<'quoted'`
heredoc может ломать парсер (воспроизведено напрямую перед тем, как перейти на
отдельный файл — этот класс проблем с экранированием так снимается полностью).

**Что можно сделать только вручную** (см. ниже): `chmod +x run_claude_analysis.sh`
и первый `launchctl load` — оба этих действия классификатор безопасности Claude
Code относит к «создание автономных агентов» и требует явного запуска
пользователем, не автоматического.

`com.disclosurebot.telegram` — единственная задача, которая должна работать
непрерывно (long polling Telegram), а не разово по расписанию; `KeepAlive`
перезапускает её, если процесс всё же завершится. Тот же шаг с Full Disk Access
для `/bin/bash` (см. выше) нужен и ей — если он уже выдан для daily/watchdog,
дополнительно делать ничего не нужно.

**Watchdog** нужен потому, что упавший бот и тихий рынок выглядят снаружи
одинаково — в обоих случаях в Telegram ничего не приходит. Он ничего не
скачивает: смотрит отметку `last_successful_run` в базе и, если последний удачный
прогон был больше `--stale-hours` (30) назад, шлёт предупреждение в Telegram.
Плюс `run_daily.sh` теперь сам сообщает о своём падении (trap на выходе), а бот
шлёт предупреждение, если какой-то источник упал или молчит несколько прогонов
подряд (`--silent-source-runs`, по умолчанию 7).

**`RunAtLoad` включён**, чтобы прогон, пропущенный из-за выключенной или спящей
машины, случился при следующей загрузке, а не потерялся до завтра. Задача
вызывается с `--if-needed`: если удачный прогон уже был за последние 20 часов,
она просто выходит — так что дублей не будет.

Логи: `data/bot.log` (полная история, ротация на 5 МБ), плюс
`data/launchd.out.log` / `data/launchd.err.log` (перезаписываются каждым прогоном)
и `data/watchdog.*.log`.

**Изменить время запуска:**

```bash
launchctl unload ~/Library/LaunchAgents/com.disclosurebot.daily.plist
```

Отредактируйте `Hour`/`Minute` в `~/Library/LaunchAgents/com.disclosurebot.daily.plist`, затем:

```bash
launchctl load -w ~/Library/LaunchAgents/com.disclosurebot.daily.plist
```

**Отключить автозапуск совсем:**

```bash

launchctl unload -w ~/Library/LaunchAgents/com.disclosurebot.watchdog.plist
rm ~/Library/LaunchAgents/com.disclosurebot.{daily,watchdog}.plist
```

```bash

```

### Пропущенные дни больше не теряются

Раньше SEC и Норвегия сканировались «скользящим окном последних N дней». При
ежедневном запуске это значило, что любой несостоявшийся прогон — упавшая задача,
длинные выходные, спящий ноутбук в 08:00 — терял свои дни навсегда и молча.
Теперь просканированные дни записываются в таблицу `scanned_days`, и каждый
прогон добирает те дни из окна, которых там ещё нет. Уже просканированный день не
стоит ни одного запроса, поэтому окно `--sec-days` можно держать широким (по
умолчанию 7): это окно **восстановления пропусков**, а не объём работы за прогон.
Чтобы после долгого простоя не случилось одного гигантского прогона, за раз
докатывается не больше `--sec-max-backfill-days` дней (по умолчанию 3), начиная с
самых свежих; остаток дотянется за следующие прогоны.

Сегодняшний день сканируется всегда и **не** помечается пройденным — его индекс
ещё пополняется. Отдельно различаются ответы SEC: 403 (выходной, праздник или
индекс ещё не опубликован) означает «день пустой, можно закрывать», а 503
(троттлинг) — «попробовать позже», и такой день намеренно остаётся
непросканированным.

## CFD-сигналы (эксперимент)

Раз в день бот ищет пробой тренда на 13 монетах (BTC, ETH, SOL, XRP, BNB, DOGE, AVAX, LTC, LINK, TRX, ENA,
HYPE, SUI) и сообщает в Telegram, что происходит с каждым сигналом. **Бот не открывает сделок и не ставит
ордеров** — это сообщения; исполнение ваше, у вашего брокера, на CFD или как вам удобно. Код: [cfd/live.py](cfd/live.py),
спецификация: [docs/superpowers/specs/2026-10-08-cfd-live-crypto-breakout.md](docs/superpowers/specs/2026-10-08-cfd-live-crypto-breakout.md).
Вызывается из `bot.py` на каждом полном прогоне, после проверки ваших позиций.

**Правило** (то, что в исследовании называется BO-D с выходом E0, те же функции `cfd/setups.py` и `cfd/exits.py`):

- на закрытии дневной свечи: **лонг**, если закрытие выше максимума предыдущих 55 свечей и выше 200-дневной
  средней; **шорт** — зеркально. У всех монет порог выброса на свече 60%;
- начальный стоп — 2,5×ATR(14) от закрытия сигнальной свечи; **вход** (справочный) — открытие следующей свечи,
  а если его ещё нет — закрытие сигнальной. R — расстояние от входа до стопа; сигнал пропускается, если R не
  больше 0,25×ATR или больше 6×ATR;
- **выход — только трейлинг-стоп**: после каждой завершённой свечи стоп подтягивается до максимума свечи минус
  3×ATR (для шорта — зеркально), назад не ходит; позиция закрывается, когда свеча прошла через стоп (по стопу,
  а при гэпе — по открытию);
- **TP1–TP4 — это отметки, а не выходы**: +1R, +2R, +3R, +4R от входа. Бот пишет, когда цена их коснулась, и
  позиция остаётся открытой. Закрытие по частям исследование не подтвердило, поэтому его нет;
- одна открытая позиция на монету. Внутри свечи стоп считается раньше новой отметки (как в бэктесте), если
  только свеча не открылась уже за отметкой.

**Сообщения** — по одному на событие, только сама сделка: новый сигнал — блок моноширинным шрифтом (пара и
сторона, вход, стоп, TP1–TP4, размер позиции в евро — при заданном балансе), отметка и закрытие — одной строкой:

```text
SOLUSD Long · CFD
Entry 121.50
Stop  108.20
TP1   134.80
TP2   148.10
TP3   161.40
TP4   174.70
Size  €46
```

```text
SOLUSD TP1 134.80 stop 119.40
SOLUSD closed 152.30 +2.32R (+€11.60)
SOLUSD closed 108.20 -1.02R (-€5.10)
```

Шорт — «Short». В строке отметки `stop` — трейлинг-стоп, действующий после неё. Без баланса нет строки Size, а
итог — только в R. Цены: 2 знака от 100, 4 знака от 1 до 100, 6 знаков ниже 1. Итог в R — после заложенных в исследовании издержек (круг 0,25% для BTC и ETH, 0,40% для
остальных; 0,06% за ночь).

**Объём и риск.** `риск € = баланс × риск% / 100`; `объём = риск € ÷ (R × курс USD→EUR)`, с округлением вниз
(до 0,0001 монеты при цене выше 100, до 0,01 от 1 до 100, до целой монеты ниже 1). Без баланса сообщение
называет риск в процентах и «объём на €1 000 баланса». Если открытый риск вместе с новым сигналом выше вашего
лимита, сигнал всё равно приходит, с пометкой «открытый риск уже N% — выше вашего лимита M%».

**Команды** (в меню — пункт 5, тот же текст):

- `/cfd` — шапка, настройки, открытые сигналы (монета, сторона, вход, стоп сейчас, отметка, дни) и итог по
  закрытым («если брать каждый сигнал»: сколько, доля прибыльных, profit factor, средний результат, сумма в R
  и в € при заданном балансе). Пока сигналов не было: «Сигналов пока не было.»
- `/cfd balance 500` — баланс в евро (`0` — убрать); `/cfd risk 1` — риск на сигнал, % (0,1–5);
  `/cfd maxrisk 3` — лимит открытого риска, % (1–20); `/cfd off` и `/cfd on` — пауза новых сигналов (открытые
  отслеживаются дальше). Каждая отвечает новой строкой настроек, неверное значение — строкой с примером.
- `/cfd plan XAUUSD buy 4461.80 stop 4449.10` — ваша собственная CFD-сделка (`cfd/plan.py`): бот не выбирает
  сделки, а считает по вашему входу и стопу четыре цели (TP1–TP4 = +1R…+4R), риск в евро и объём от баланса
  и риска `/cfd`, и затем следит за ценой (минутные бары Yahoo, раз в 5 минут) и пишет на каждой цели и на
  стопе. На каждой цели закрывается четверть; стоп после TP1 — на вход, после TP2 — на TP1, после TP3 — на
  TP2. Инструменты: 16 валютных пар, золото, серебро, нефть, 6 индексов, 13 монет (можно `gold`, `eur/usd`,
  `btc`). У золота, серебра и нефти на Yahoo есть только фьючерс: бот запоминает разницу с вашей ценой входа
  в момент команды и следит с этой поправкой. Сделка считается открытой в момент команды; если цена далеко
  от входа или уже за стопом, бот даёт только расчёт. Итог — в R и в евро (R × риск), без издержек брокера.
  `/cfd cancel 3` — перестать следить. Приказы бот не выставляет.

Сообщение уходит, и только после этого сигнал сохраняется в таблице `cfd_signals`: если отправка не удалась,
следующий прогон повторит то же событие без дублей. Сбой по одной монете пишется в лог, остальные идут дальше.
Прогон с `--no-telegram` и прогоны по отдельным источникам (`--sec-only` и т. п.) этот шаг пропускают.

**Что известно о правиле — честно, в трёх строках:**

1. Это решение пользователя, а не прохождение заранее заданного порога: предрегистрированный отбор оценивал
   выход четырьмя тейк-профитами и не включил ничего.
2. Вне выборки трейлинг-выход прибылен: profit factor 1,60 на 11 альтах и 2,12 на BTC и ETH.
3. Но это ниже заранее заданной планки значимости, и результат держится на нескольких очень крупных сделках —
   поэтому везде пометка «эксперимент». Подробности — в [docs/cfd/](docs/cfd/) (`BACKTEST_REPORT_R2.md`,
   `EXPLORATORY_NOTES.md`).

## EURUSD carry-gated: сигнал в Telegram (отдельная функция, не про раскрытия)

[carry_strategy.py](carry_strategy.py) — headless Python-версия отдельно
провалидированной дневной стратегии `EURUSD carry-gated trend` (проект
`~/forex-daytrader`, Pine-скрипт в TradingView). Раз в день (внутри
`run_daily.sh`, после раскрытий) пересчитывает сигнал и шлёт в тот же Telegram,
но **только при смене состояния** (flat→long/short, выход) — не каждый день.

**Правило (заморожено, не переподбирать):** long, когда цена больше чем на 2.5%
выше 200-дневной средней **и** доходность немецких 2-летних бумаг выше
американских (расхождение политики ЕЦБ/ФРС); short — зеркально. Выход — либо
цена вернулась через среднюю, либо трейлинг-стоп 6×ATR. Провалидировано на Pine
(OANDA/FX_IDC, 2002–2026): OOS profit factor 1.92, +20.6%, 15 сделок — «лучший
найденный кандидат», не доказанное преимущество (детали и все оговорки — в
заголовке самого Pine-скрипта).

Это **отдельный** от Pine-скрипта расчёт, не обёртка над ним: TradingView
Desktop с интерактивной MCP-сессией недоступен headless-процессу, поэтому
сигнал пересчитывается заново по независимым бесплатным источникам:

| Данные | Источник | Ключ/логин |
|---|---|---|
| Цена EURUSD | yfinance `EURUSD=X` | не нужен |
| Доходность DE 2y | Bundesbank API (`BBSSY.D.REN.EUR.A610.000000WT0202.A`) | не нужен |
| Доходность US 2y | FRED, серия `DGS2` | не нужен |

Как и весь остальной проект — только факты и число, без вердикта «войти/не
входить»: при входе сообщение называет цену, среднюю, спред и начальный стоп (6×ATR),
но исполнение ручное, как у gold-конфига в `~/forex-daytrader/alerts_config.md`
(та же логика: «если не можете следить каждый час, поставьте трейлинг-стоп у
брокера на этом расстоянии» — здесь то же самое, но раз в день, а не раз в час).
Бот не держит позицию у брокера и не шлёт ежедневные «ещё держим» — только
переходы состояния.

Сообщение — одна короткая строка в том же виде, что и остальные сигналы (точка: 🟢 лонг,
🔴 шорт, ⚪ выход во флэт):

```text
🟢 EURUSD!: вход в лонг (новый сигнал) — цена 1,2000, 200-дн. средняя 1,1500, спред DE-US 2 г. +0,35 п.п., стоп ~1,1520 (6×ATR)
🔴 EURUSD!: вход в шорт (новый сигнал) — цена 1,1000, 200-дн. средняя 1,1500, спред DE-US 2 г. −0,35 п.п., стоп ~1,1480 (6×ATR)
⚪ EURUSD!: выход во флэт (сработал стоп) — цена 1,1600, выход ~1,1670
```

«Спред» — доходность немецких 2-летних бумаг минус американских, в процентных пунктах.
Выход при стопе называет уровень стопа, при снятии сигнала — цену закрытия.

`python carry_strategy.py --status` — текущее состояние (flat/long/short).
`python carry_strategy.py --once --dry-run` — что было бы отправлено, без
отправки и без сохранения состояния.

## Важно

- Это агрегатор публичных раскрытий, а не торговый советник и не бот для
  автоматической торговли. Он ничего не покупает и не продаёт, только
  показывает уже опубликованные сделки. Счёт Trading 212 он только читает
  (см. «Trading 212»): разместить, изменить или отменить заявку бот не может.
- Список S&P100+Nasdaq100 ([universe.py](universe.py)) кэшируется на 7 дней в
  `data/universe_cache.json`. Тикеры — с Wikipedia, CIK для точного матчинга
  по SEC-заявкам — из официального `company_tickers.json` самой SEC.
- Кластерный сигнал считает разных людей по имени (SEC — `owner_name`, House —
  `member_name`, BaFin — `notifier_name`, Норвегия — `person`); в редких случаях
  совпадения ФИО у разных людей это может задвоить/занизить счётчик — для
  практических целей это не критично.
- Курсы валют для сигналов ([fx.py](fx.py)) — дневные, с Yahoo Finance, кэш в
  `kv_cache` на сутки. Это пересчёт «для сравнимости сумм», а не бухгалтерия:
  сделка пересчитывается по **сегодняшнему** курсу, а не по курсу на дату
  сделки. Для «эти двое купили один тикер на крупную сумму» этого достаточно.
- Норвегия: сумма/цена сделки в источнике не структурирована (свободный текст
  уведомления) — парсится регуляркой с проверкой на разумность (см. раздел про
  Норвегию выше и [norway.py](norway.py)). Денежная сумма и тикер надёжны;
  имя покупателя — best-effort, в единичных нетиповых формулировках может
  оказаться неидеальным, это не влияет на точность сигналов по деньгам/тикеру.
- House-парсер читает текстовый слой PDF по координатам слов; при изменении
  вёрстки формы Клерком его может понадобиться поправить.
- `insider_score.py` (порог «топовый инсайдер по доходности») оставлен в коде
  как опциональный доп.фильтр (`--require-top-insider`), но по умолчанию
  выключен — за все тесты ни разу не сработал, кластерные сигналы оказались
  практичнее.
- Мусорные «тикеры». Некоторые эмитенты (неторгуемые фонды, пустышки) подают
  Form 4 с `issuerTradingSymbol` = буквально `NONE` или `N/A`. Такое значение
  становилось ключом группировки и сводило разные компании в один фиктивный
  «тикер» — это уже приводило к реальному отправленному сигналу. Теперь такие
  значения превращаются в NULL при разборе (`sec_edgar.clean_ticker`) и вдобавок
  отфильтровываются в SQL для строк, собранных раньше.
- Один и тот же документ SEC перечислен в дневном индексе по разу на каждого
  со-подателя (эмитент + отчитывающееся лицо), то есть ровно вдвое чаще, чем нужно.
  Дубли теперь отсеиваются сразу: на 04.09.2026 это 934 строки индекса → 458
  уникальных документов, то есть вдвое меньше запросов и по Form 4 тоже.
- Шведские свопы декларируются с номиналом **и** в колонке объёма, **и** в колонке
  цены, поэтому «объём × цена» даёт бессмыслицу (порядка 10^16 крон). Значения
  выше `sweden.MAX_PLAUSIBLE_VALUE` считаются неразобранными и пропускаются — по
  той же логике, по которой Норвегия пропускает уведомление, сумму в котором не
  удалось распознать.
- Form 4 всегда содержал поля, которые бот выбрасывал: `aff10b5One` (сделка по
  заранее составленному плану 10b5-1), `postTransactionAmounts` (сколько акций
  осталось после — отсюда прирост к позиции), `directOrIndirectOwnership` и дату
  подачи из дневного индекса (отсюда лаг раскрытия). Теперь всё это читается.
  Строки, собранные раньше, этих значений не имеют — признаки заполнятся только на
  новых данных.
- Балл сигнала — это порядок внимания, а не прогноз. Веса выбраны рассуждением и
  проверяются через `backtest.py`, а не наоборот.
- `last_members` в `cluster_alert_state` хранится как JSON. Раньше имена
  склеивались через запятую, а в именах запятые встречаются постоянно
  («CASCADE INVESTMENT, L.L.C.») — одно имя читалось обратно как два, множества
  никогда не совпадали, и сигнал уходил бы заново каждый прогон.
